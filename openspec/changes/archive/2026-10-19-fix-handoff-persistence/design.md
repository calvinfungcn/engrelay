# Design

## Context

问题动机见 [proposal.md](proposal.md)。本设计基于 v1.9.2 的实际源码，不把过去归档或接案摘要当作新验收。

| 已核对位置 | 现有能力及缺口 |
| --- | --- |
| `payload/docs/ai-collaboration/agent-prompts.md` 的 Common Preflight、Implementation Engineer、Code Reviewer | 已要求真实边界校验，并允许必要产物或完整响应 fallback；实际派发仍可能把所有 `.ai/` 写入禁止，同时未明确替代交接输出。 |
| 同目录 `handoff-schema.md` 的 General Rules、Response Handoff Fallback | 已有落盘、文件过期和下一可写角色持久化要求，缺少可核对的写回完成条件及来源匹配的恢复顺序。 |
| `skills/ai-collab-continue/SKILL.md` | 会读审查索引，但先按 live handoff 分流；没有明确处理“审查已完成、文件仍派发原审查”的路径。 |
| `scripts/validate-runtime-state.ps1` | 当前参数仅 WorkspaceRoot、CurrentTaskPath、HandoffPath；Get-FieldValue 返回首个匹配，State revision 只校验语法，exit 0 明示不验证证据新鲜度。 |
| `scripts/test-validate-runtime-state.ps1` | 已有 GUID 可丢弃目录、子进程退出码/诊断检查及 CaseFilter，可扩展传参覆盖新增可选行为。 |

先使用知识图谱定位符号，再直接核对源码：两份 PowerShell 文件存在部分或不可用的索引覆盖，不能依赖图谱证明完整调用关系。真实项目仅作为前轮观察来源，不复制其文件、路径、日志或审查原文；此处及夹具仅使用虚构批次。

后续 Git 历史核对覆盖 v1.7.0 至 v1.9.2：Implementation Engineer 和 Code Reviewer 角色段落在六个标签中相同，严格只读 fallback 与下一可写角色持久化的规则从公开首版提交 `9c26c22` 已存在；`6397550`、`38ec979`、`d8ff3fa` 未取消正常交接写回要求。未定位到近期新引入该核心规则的提交，也不据此证明文案变化对模型行为绝无影响。本次修订补齐既有分支的执行责任，不把潜在缺口误报为已经证实的近期回归。

## Goals / Non-Goals

**Goals:**

- 在一个连贯批次内，使正常交接的写入可被回读确认，使受限交接可由有权限者安全恢复。
- 对调用方明确给出的预期状态提供可执行检查，同时保持无参数调用兼容。
- 复用已有 handoff、审查记录、索引和外置检查容器，保持摘要简短。

**Non-Goals:**

- 不增加新的 Routing 字段、动作、状态、状态库、待处理队列、通用恢复命令或第二份实施清单。
- 不提供多文件原子事务、锁服务、自动唤醒、意外断线的零丢失保证或真实性认证。
- 不修改真实项目、不迁移历史、不重建当前发行 snapshot，不在本次规划中提交、发布或部署。

## Decisions

### 1. Minimal Option and feasibility

采用“现有规范约束写入者与接续者 + validator 可选预期比对”。写入及恢复仍由具备权限的活跃 Agent 执行；没有后台服务，也不新增自动文件修改器。本次只落实已确认缺陷和因果必要保护，没有新增产品范围。

只补文案成本最低，但仍不能机械识别语法正确的旧路由；这不足以满足已确认的预期比对。建设宿主钩子、常驻协调器和原子状态层会引入进程生命周期、平台适配、权限及并发维护，投入显著高于本批价值，留在非目标。五个可选 CLI 参数是为当前交接正确性增加的有限公共契约，不泛化为任意字段查询。

可行性结论为 proceed：已有 scoped Markdown 读取、错误聚合、子进程夹具和角色边界可复用；不需要数据库、外部服务或人类环境准备。一个 M 批次，预计一至两个实施会话。首个可见结果是：夹具中原文件仍派发审查且计数 1，完成的明确审查交接改为修复且计数 2；旧文件的预期检查失败，获准恢复并回读后检查成功，原审查不重跑。

### 2. Permission and output contract

在正式派发的 Next output files 与 Operator Command 中共同列出审查记录、索引和 `.ai/handoff.md` 的写入许可。默认“业务代码只读”不禁止这些明确产物；对 current-task、tasks.md 等其他输出仍按原角色权限逐项决定，不扩大为任意文件可写。

派发者不得仅因审查独立、泛称“只读审查”或个人偏好，给本来获准维护的工作流产物自行增加 `.ai/` 禁写限制。严格限制须有用户/适用上位指令的明确要求或实际工具权限依据，并在原有状态/限制叙述中简短说明来源；不新增来源机器字段。使用宿主实际只读的审查代理仍属允许路径，其权限不被扩大，由下述可写负责者承接落盘。

用户或适用上位指令明确禁止、实际工具拒绝时，受限角色沿用响应 fallback；生成指令必须说明这一出口，不能只要求 findings 和 verdict，也不能用本契约解除真实禁令。仅咨询/局部意见不默认接管 live 状态。Common Preflight、角色出口、三种运行态模板、canonical README 的同义重述及必要的 agent-rules 说明引用同一 schema，避免多处复制恢复算法。

委派只读子代理后，若发起委派的主 Agent 或当前负责 Agent 仍活跃且已获准更新 handoff，必须在本次对外交接结束前核对返回内容、同批次来源、执行归属和实际 verdict，完成落盘、回读及校验；不能明知有可写负责者仍推迟给下一角色或要求用户手写文件。子代理的只读限制继续有效；主 Agent 只发布有效来源的决议，不冒充原审查者、不自审、不新增 verdict。没有可写负责者、存在上位禁令或来源冲突时才保持未持久化的诚实出口。此责任只适用于已有活跃负责者，不要求启动新主进程或恢复服务。

### 3. Boundary persistence and read-back

只在真实转移、等待、计划会话中断及关闭处执行；连续同职责微步骤保持原成本。

1. 形成当前获授权的完整下一状态，依据实际完成 verdict 决定累计值，保存原 handoff 的字节指纹及已有 revision 作为本次转移依据。
2. 核对同批次执行归属；写前重新检查原文件未发生意外变化。发现其他写入或不一致时停止覆盖并说明具体冲突，不争抢进程。
3. 写入完整 handoff，回读与刚形成的意图核对，至少包含批次、动作、下一角色、累计计数和已有 revision；已有 revision 在新转移时递增，恢复同一次转移不再递增。无历史 revision 的兼容记录不要求补历史序列。
4. 执行原结构校验；新增接口实施后，采用本次新版契约的真实边界必须同时传入本次意图对应的预期批次、动作、下一角色和累计计数，已有 revision 时再传该值。预期不得从回读的旧文件重新生成，否则会形成空洞自证。接口尚未实施的本次规划修订只能执行原结构检查并人工核对意图，不能声称新参数已通过。
5. 在已有 result、审查记录或外置边界日志记录命令、退出码、诊断及输入对应关系。最终回复用一句话说明“已更新文件”或“未持久化及原因”；不在 handoff 添加回执字段，不把校验输出再写回被检文件。

可恢复错误由当前角色在权限内修正；权限不足使用完整 fallback，不报告持久化成功或普通 accepted。沿用原关闭证据规则，不自动回滚为更旧状态，不把半完成的跨文件更新当作事务成功。

### 4. Durable fallback and bounded recovery

有权限写正式审查产物时，在同轮报告现有 Next Actions 下用外层围栏保存一份完整 Response Handoff，外层围栏长于内层围栏，恢复时提取其中完整 Markdown；索引仅链接，不新增 pending 文件或审查模板章节。来源 change、batch、旧 revision（若有）和旧 handoff SHA256 放在现有 Evidence/Next Actions 的叙述中，完整交接保留来源角色、实际 verdict 和下一出口。所有文件均只读或没有可写审查产物时，回复携带相同匹配信息和完整交接；后续若拿不到来源，只能指出缺失，不能恢复内存中的猜测。有活跃可写负责者时，本段是其当轮发布的输入，不能被当作延迟落盘的理由。

接续按以下顺序处理：

- 先核对 current-task、live handoff、明确的同批次 review index 及所链接交接；不遍历全历史，也不按文件时间或最高编号选权威。
- live 已关闭、真实等待、预算或有限授权、角色权限及独立性仍有效。候选不能绕过这些边界，不能把已闭批次改回 open。
- 候选是同批次已完成、明确替代当前旧路由的转移，来源 revision/字节指纹匹配，且无更新状态或并发写者时，获准维护交接的负责 Agent 可先保存该来源决议。持久化后再决定自身是否有资格执行下一角色；复制决议不等于接任角色，也不能把恢复者写成原审查者。
- 恢复保留来源角色/Agent、批次、范围、实际累计 verdict、命令和风险；不再计一次审查，不重跑旧命令。原指令中“文件未更新”说明放入历史 delta，不把它当作恢复后仍然未落盘的当前事实。
- live 已引用并应用该来源或已前进时不再发布；哈希不同、存在多个矛盾候选、缺少关键输入或归属不明时保留有效状态并给出最小恢复方向。即使相同字段看似接近，也不凭猜测把计数降回来源值。
- 新 fallback 提供上述匹配依据；旧记录不强制回填，仅在已有明确证据足以无歧义确认来源时按原规则恢复。恢复 close 仍须具有原关闭决议、适用角色及匹配的最终检查依据，不能由旧 exit 0 合成新的普通 accepted。

来源匹配用现有 .NET/PowerShell 文件哈希能力；只增加既有报告的必要证据叙述，不增加运行态机器字段或第二权威。检查与写入间仍可能有竞态：本批只做可见归属及写前/回读保护，不宣称原子 compare-and-swap。

### 5. Optional expected-state interface

在 `validate-runtime-state.ps1` 新增以下可选字符串参数；使用是否绑定区分“省略”与显式空值/数字 0，避免数值默认值误判。

| 参数 | 比对对象与约束 |
| --- | --- |
| `ExpectedBatchId` | 非空；与 current-task 批次及 Routing 中批次精确一致，采用 ordinal 比较，禁止前缀匹配。只要绑定任一预期参数就必须提供它。 |
| `ExpectedNextAction` | continue、dispatch、close 之一；比对实际唯一动作。 |
| `ExpectedNextRole` | 非空；精确比对现有角色名称或 none，不引入新角色枚举。 |
| `ExpectedReviewRound` | 非负十进制整数，0 是有效且已提供的值；与实际累计值比较，规范化前导零且不做可能溢出的窄整数转换。 |
| `ExpectedStateRevision` | 正十进制整数；要求实际存在并相同，不推导历史最新 revision。 |

仅提供 ExpectedBatchId 也执行批次检查；其他省略字段不强制加入旧记录。绑定空字符串或非法值明确返回 exit 1；无预期参数时原输出、退出及兼容规则保持不变。开启预期检查时，从唯一真实二级 Routing 提取所给字段；重复 Routing 或对应字段、缺失字段均失败，围栏示例及其他段落不补位。复用 Get-MarkdownStructure 等已有能力并局部规范化标题；不扩大原默认解析规则，也不直接把返回首个匹配的 Get-FieldValue 当成“唯一”证明。

原结构错误继续聚合且不能被预期匹配覆盖。匹配成功可在原结构成功行之外增加一条仅说明“与所给预期一致”的信息；不传参数时保持原文本。脚本始终只读，不访问 review index 选择路由，也不认证预期值本身。参数可选只保证旧 CLI 调用兼容；新版契约的负责角色在接口可用时必须传批次、动作、下一角色和累计计数，存在 revision 时附该值。无参数 exit 0 可以是合法的旧结构检查，但不是本次新版交接已履行预期比对义务的证据。

### 6. Focused verification and role routing

唯一实施进度见 [tasks.md](tasks.md)，不另建计划清单。新增机器检查扩展现有 validator 测试 helper 传入参数，继续验证真实子进程退出和诊断；新增匹配正例及结构有效但状态不符的反例，保留旧调用回归。实现后分别用 Windows PowerShell 5.1 和 PowerShell 7 执行定向新增用例及本 validator 全套，因该共享脚本改变而需要一次完整兼容回归，无须重跑安装全生命周期。

角色协议不能由字符串存在测试证明。用虚构可丢弃目录实际演练保存/回读、仅准审查产物 fallback、写入失败、同批恢复、重复恢复、跨批冲突、已有 close、额度/独立性保护和计划会话 continue；记录执行者、输入、步骤、实际变化及未验证限制，不把人工或脚本推演说成 CLI/IDE 已遵从，也不额外建设运行器。

完整缺陷演练须串联真实落盘结果：虚构同批 handoff 仍为审查前计数 1、完成的审查记录为计数 2 且下一角色为 Fix Engineer；旧文件无参数结构检查可以通过，但新版预期检查必须检出差异；合法来源经获准负责者写回、回读后预期检查通过，再接续时不能重跑审查或多计一次 verdict。分别覆盖普通可写审查、只读子代理返回后可写主 Agent 当轮发布，以及真实禁写且无可写负责者时只交付完整 fallback。每条记录前后文件、实际执行步骤和外置检查依据；生成的普通审查指令不得自行带入无来源 `.ai/` 禁令。复用现有夹具和现有代理能力，不为演练建设宿主运行器，也不把合成演练宣传为实际宿主已验证。

Design Review Decision：首版需要独立设计审查且已完成。round 01 对其记录哈希对应的首版给出 PASS；当前实际累计 verdict 为 1，剩余默认额度为 2。本次用户明确确认的细化保持同一意图、五参数接口、状态权威、风险及任务 ID，不新增复杂性例外；不自动再开设计审查，也不把首版 PASS 说成修订版已独立审查。原审查记录保持原样，DR-01 至 DR-06 仍待实施者按原指派落实和最终独立代码审查核对。本次修订不产生新 PASS/REVISE verdict，1.1 保持完成；后续独立 M 代码审查覆盖最终修订，必要的原范围复核仍计入剩余额度，不自动第四轮。若后来确有实质设计变化，按原规则重新确定所需审查，不能以本段豁免。

## Risks / Trade-offs

- [默认权限被误解为任意写权限] → 逐项列出允许产物，保留明确禁令和实际工具权限；咨询不创建运行态。
- [恢复覆盖新路由或把旧 verdict 再计一次] → 同批来源匹配、写前重读、已应用识别及实际累计值；矛盾时不覆盖。
- [预期从旧文件反推造成形式检查] → 预期必须来自已决定的转移；回读内容与意图核对，来源可追溯但不宣称认证。
- [多文件部分完成或无预告崩溃] → 只报告实际保存结果，下一会话据明确存留证据恢复；不保证零丢失或原子发布。
- [交接膨胀与 token 成本] → 来源完整交接只存一份既有报告，索引和 handoff 链接；最终回复只加短持久化结果。
- [旧包不认识新参数] → 仅新脚本调用新接口，不要求旧包调用；旧记录无需回填，无参数保持兼容。

## Migration Plan

只修改 canonical 产品源和必要双语说明，不编辑生成宿主副本、历史归档和真实项目。验证中使用 GUID 可丢弃目录；检查证据留在受忽略本批目录或实际正式审查记录。发行时才在获授权干净导出重建清单并按原管理器升级，本次不发布。若后续需要撤回，回退该契约与新增可选参数的源码差异并重新验证即可；不自动修改项目运行态、回写旧报告或伪造发行清单。
