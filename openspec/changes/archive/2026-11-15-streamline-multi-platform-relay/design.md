# Design

## Context

动机见 [proposal.md](proposal.md)。现有 Full 的累计三次门槛同时写在 `agent-rules.md`、角色规则及 `validate-runtime-state.ps1`；Lite 在自身 `RULES.md` 和 `validate-state.ps1` 独立执行同样的门槛。两个校验器均读取既有 `review-budget-extension`；这些是升级时必须一起考虑的行为，不是只改提示词即可解决的问题。

仓库已具备人工转交、自包含指令、C1–C5 默认表、按入口和输入复用证据、Lite 顺序队列及关闭提示。本方案复用它们。用户明确授权一个提案分三阶段实施；Task Owner 自选平台、模型和推理强度。Full 默认人工接力，Lite 仅在用户选用人工接力时暂停。

## Goals / Non-Goals

**Goals:** 在不重复确认已有授权的情况下继续提案；仅在实际不收敛或真实限制时中断受影响工作；在新旧语义切换时保留有限授权、历史和独立性。第一批能用一个虚构场景展示从关闭到下一工作、独立审查及三次后仍可安全接续。

**Non-Goals:** 新 Agent 调度器、模型服务、自动跨平台调用、审查者身份认证、新运行状态或第二份实施清单；WM 项目的数据库／认证夹具与真实安装；默认完整宿主矩阵和未经测量的 token 承诺。

## Decisions

### 1. 已授权提案在真实边界接续

Full 接续在关闭后先读取当前任务、handoff、原关闭依据和唯一 `tasks.md`。如果现有书面任务或明确的当前请求已经授权持续实施唯一父提案，且下一范围、依赖、执行归属和权限能无歧义确定，使用已有 Task Intake 准备下一批。多个无先后依据的候选、只授权已结束范围、真实等待或不明确的负责人决定，给出实际状态和最小后续请求。不能仅因父提案存在就推断授权。

已关闭批次的 `owner-decision` 仍仅说明该范围有限接受；未完成的技术条件仍未验证。后续工作不重放旧 Operator Command，不撤销明确的“只审查一次”等范围限制。Lite 仍以自身已批准队列和依赖为权威，不调用 Full Skill。

保留人工接力的实际角色边界：保存、回读、核对预期后停止；由用户选择能获取所需文件的工具及其模型和推理强度。共享工作区读取当前文件；非共享工具仅接收经用户审阅的最小材料，沿用现有响应交接和来源匹配，不宣称写回。C1–C5 沿用现有默认与覆盖规则，不新增模型映射、模型分析或资格门槛。

替代方案是合并入口或自动启动下一平台；前者会改变兼容名称，后者违背用户选择平台的需求，因此均不采用。

### 2. 将真实 verdict 与不收敛处理分开

保留 `Review round`、审查文件和索引的真实编号及现有单调记录；完成一次设计、代码、验证或裁定才按现行语义记一次。普通失败检查、未启动的验证、保存交接或环境等待不自行伪造 verdict。默认数值 3 不再单独限制新版本的已授权可执行动作；M/H 的独立审查、实际验收和手动转交照常适用。

同一未解决发现的一个循环是一次有范围的修复及其独立复核。连续两个这样的循环均没有**已核对且缩小根因或消除既有阻碍的新证据**，也没有被独立核验的实质改善时，暂停该发现的重复循环，在现有审查记录／handoff 中引用两次结果、剩余风险及最小下一步。换文件名、角色、模型、表述、时间戳或重复旧日志不构成进展；不同问题的改善不能掩盖该问题的停滞。现有证据不能判断时保留未知，先核对具名记录，不凭猜测宣布有进展。

有权负责角色可在原范围内作技术分析并提出可执行处理；只有涉及实际授权、业务取舍、风险、明显超预期成本或确实无法在现有条件继续时才走负责人决定出口。不能借这个规则无上限地反复派发其他同样失败的角色。新增问题若扩大原范围，仍按现有授权处理。

每次审查保留自己的范围和原有全局文件编号。某次 verdict 确实覆盖当前未完成验收才关联其计数；同一发现换名或拆批不能消除相关历史。若两个子范围都被前三轮覆盖，第四轮只覆盖其中一个，后续另一个范围不自动把第四轮当作自己的验证；证据不足时不猜测。**已写入的有效有限授权和已记录计数不做追溯重算**，例如已有 `from=4; through=6` 时仍按 4 至 6 处理，不能为了获得新空间改成 3。

替代方案是把默认三次改为更大的固定数；它仍会把正常设计与独立验证误判为重复循环，因此不选。只删除全部收敛约束会失去对真实反复失败的保护，也不选。

### 3. 显式限制、结构校验与迁移

新版本保留结构化 `Task Owner decision: review-budget-extension` 的既有键、批次匹配、`from`／`through` 和有限范围。当前动作依赖该授权时，只有字段完整有效、身份／任务匹配且 `from <= Review round < through` 可通过其结构检查；到 `through`、字段冲突或无效时，可执行继续和 Agent 派发不能把该授权当作不存在来放行。合法等待、真实 blocked 和 close 仍可表达。单次审查授权不自动授权修复。正文中的明确限制即使脚本无法理解，负责 Agent 仍须执行；结构通过不证明授权真实性或范围。

Full／Lite 的同一次候选交付需要同时协调 canonical 规则、入口、受管 `agent-rules.md`、模板及对应校验器。无明确有限授权的旧交接在升级后继续可读，保留原字段和真实计数；用户要求继续时，只有原等待**仅由旧默认三次门槛造成**且适用工作已有授权、无其他等待或归属冲突，才可按新规则恢复。真实负责人决定、环境等待及已关闭批次不会因此自动重开。原 handoff 若已有适用显式限制，限制优先；不要求回填历史或重新批准原范围。

行为兼容性有明确边界：同一个 `Review round: 3` 交接在旧脚本可能非零，在新脚本可能通过。只有项目完整升级到匹配的新包后才能按新规则执行；旧包、未升级的宿主副本或项目自有规则可能仍拒绝或冲突，应指出版本与冲突来源，由项目按适用授权协调，不选择性换脚本绕过限制。回退时使用受保护的匹配旧包和现有恢复材料；旧脚本可能再次阻断，不能改写计数或扩大授权。真实项目升级／回退本变更不自动执行。

状态校验仍只检查可表达的结构、预期状态和结构化限制，不判断某个自然语言决定是否真实、审查是否独立、停滞是否发生或业务是否验收。对损坏或语义冲突的显式限制不得静默视为无上限；脚本不能判定的内容由负责角色核实并保留未知。

### 4. 环境、证据和上下文

当验收依赖认证入口、隔离数据或样本，负责人在准备相关验证前先复用已有项目指引与就绪证据，确认依赖、能否安全访问和具体恢复条件。不可用时保留对应未验证项，安排不依赖该条件、已授权且无冲突的工作；不因等待人为制造验证 verdict。缺失条件没有变化时，不反复派发同一项注定无法执行的验证；出现新条件后再做适用的独立验证。

按入口、输入、环境和结果判断证据是否仍适用，相关代码、配置、调用方或持久数据变化时重新核对受影响部分。模拟、纯函数或结构验证不能证明真实认证／数据库路径。交接只提供现有最小状态和具名证据链接，按角色及实际变化读取，不建立缓存清单。评分沿用既有规则：有证据的实现或修复问题可评分，环境不足单独说明；无法归因用 `not scored` 或未知。

替代方案是构建通用数据库测试框架或要求每个角色加载完整历史；这些增加项目集成与 token 成本，不是本次必要能力。

### 5. 三阶段、批次与检查

| 阶段 | 结果 | 主要交付 |
| --- | --- | --- |
| 1 | 已授权提案能接续；完整包内 Full/Lite 正常 verdict、明确限额与停滞处理一致 | 协调现有规则、入口、校验器、受管入口及针对这些行为的检查 |
| 2 | 缺环境时可继续独立工作，交接能帮助人工选模型且只读取相关依据 | 复用既有环境预告、证据和能力字段，更新受影响双语指南与示例 |
| 3 | 用有界虚构场景核对整条接力及兼容性 | 记录实际结构／场景检查与未观察宿主、未测 token 的限制 |

三个阶段共享一个变更与一个 `tasks.md`，不是自动制造三次设计或完整审查。第一批为阶段 1 的一条纵向行为（Full/Lite 规则、对应校验和测试一起完成），设计审查覆盖整体方案。若无法在一两个实施会话内完成，由同一角色在会话边界交接继续，不按文件拆批或重置计数；阶段 2 是可区分的环境和用户体验范围，阶段 3 使用既有独立审查／验证结论并按实际需要进行有界演练。是否拆出后续批次依实际范围和授权决定，相关历史必须关联。

首批检查使用可丢弃的合成状态，至少覆盖：已授权关闭后接续与未授权候选；设计／代码／验证三个 verdict 后的下一动作；`from=4 through=6` 在 4、5、6 的路由；一个仅含单次追加审查的范围；两次无进展与有效进展；环境未知及恢复；不同范围的历史关联；旧格式及无预期调用。旧字段、命令围栏、来源匹配、只读、独立性和人工停止仍覆盖原有直接影响。需要真实 Agent 的结论须有实际调用及可复查结果；如果不可用，报告未观察，不用静态检查代替。

现有代码入口包括 `payload/docs/ai-collaboration/skills/`、Full `scripts/validate-runtime-state.ps1`、Lite `scripts/validate-state.ps1`、相关测试与 `agent-rules.md`。同时更新 `README.md`／`README.zh-CN.md` 及适用人类指南和双语 CHANGELOG 的候选说明；不把源码候选写成已发布版本。只在真实发行准备且获授权时从干净导出生成快照。

## Risks / Trade-offs

- [移除固定三次门槛可能使错误修复无限循环] → 对同一发现设置两个无进展循环后的技术处置，保留现有成本和授权边界；不依赖脚本虚构语义判断。
- [两次无进展的证据判断有主观性] → 使用既有具名 findings、实际版本和独立复核结果；只有经核对且能缩小根因／消除阻碍的证据才算进展，未知不自动放行。
- [旧包、新包及项目自有规则混用产生冲突] → 原样保留旧格式和明确有限授权，完整升级时协调受管入口及两套校验；说明退出结果语义变化和回退限制。
- [环境检查可能变为新增审批] → 仅针对实际验收依赖做轻量核对；不依赖环境的已授权工作继续，真实不可得的证据保持未验证。
- [设计与验证产生额外会话] → 因本次修改的是审查门槛和独立性边界，安排一次独立设计审查；后续集中审查并只复核受影响内容，不为每个阶段制造审查。
- [实际多平台宿主与 token 无法保证] → 使用可得的有界证据并如实标明层次；未实际调用的平台与未测数据保持未知。

## Migration Plan

1. 先在同一候选中实现阶段 1 的规则与 Full/Lite 校验一致性，检查旧记录、明确有限授权、机器字段和受管入口；不在部分更新状态宣称可交付。
2. 完成阶段 2 和阶段 3 的适用检查、独立审查与未验证项记录。原快照、历史 Review 和旧用户项目不改写。
3. 仅在用户单独授权发行或真实项目升级后，使用现有完整包与受保护的官方流程；由项目协调管理块外的自有约束。回退使用匹配旧包及原有恢复材料，旧默认门槛可能恢复生效。

## Open Questions

无阻碍当前设计的未决业务问题。哪些平台可参加后续实际演练和实际 token 数据能否取得取决于当时的权限与工具；不足时记录未观察，不改变本提案的安全边界。
