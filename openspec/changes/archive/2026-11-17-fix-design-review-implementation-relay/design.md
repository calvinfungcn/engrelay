# Design

## Context

动机见 [proposal.md](proposal.md)。本次只协调 Full 既有协议，不改变工具运行逻辑。

| 现行位置 | 已观察的约束与缺口 |
| --- | --- |
| `payload/docs/ai-collaboration/README.md#execution-batch` | 批次可以独立关闭，但未直接解释设计角色结束与独立设计交付的区别。 |
| `agent-prompts.md#design-reviewer`、`workflows.md#2b-design-review` 及 Routing Matrix | 评审通过统一写成派发 Architect 或 Implementation Engineer，没有对应合法独立设计关闭的分支。 |
| `README.md#closed-batch-guidance`、两个入口 Skill | 已有授权复用和 Task Intake 路径，应补齐显眼的设计关闭接续提示并保留当前角色停止边界。 |
| 两个任务/交接模板、`agent-rules.md` | 批次映射/phase 描述需要明确指向交付验收；没有提醒核对已有叙述中的过时评审状态。 |
| `handoff-schema.md#accepted-closure-validation` | 校验仅证明指定结构及映射，不推导自然语言目标或证明宿主遵从；本次不增加语义解析。 |

已核实的是记录与规则之间的衔接缺口，不能仅凭记录断定某次脚本错误或还原某位 Agent 当时收到的全部指令。公开资料使用下文虚构场景。

## Goals / Non-Goals

**Goals:**

- 使设计通过后的当前批次路由、独立设计交付关闭和后续实施入口可以相互核对。
- 复用已有授权、路由、模板和证据接口，让操作者能直接选择下一平台。
- 修复活动叙述的事实不一致，同时让稳定任务定义和历史记录保持稳定。

**Non-Goals:**

- 不新增角色、字段、机器状态、审批或运行引擎，不改 Lite、manager、validator 或安装投影。
- 不自动取得业务环境、运行付费平台演练或把静态推演作为真实模型遵从证明。
- 不在本设计批次中授权归档、提交、发布、真实项目安装或全局设置。

## Decisions

### 1. 先确定交付范围，再选角色出口

角色承担阶段职责，停止当前角色或当前会话不会自动满足批次验收。普通实施批次的映射应覆盖一个最小连贯交付，包括需要的设计、实施和检查；不因派给多个平台而把每个角色机械拆成独立接受批次。

独立设计交付仍然有效：它必须对应可核对的已确认交付目标，或有依据的独立可验收契约边界，例如交给外部团队评估的接口方案；在既有 Scope/Acceptance Criteria 中说明即可，无需新字段或再次批准。单凭角色名称、只勾选设计项或“本轮仅做首席设计师”不足以建立独立批次接受依据。

| 已核实情况 | 正常出口（仍先应用真实等待和有限授权） |
| --- | --- |
| 设计通过，同批仍有已授权未完成实施 | 派发 Implementation Engineer；仅在已有规则确有需要时经过 Architect 等中间角色，保存人工交接后停止。 |
| 有依据的独立设计交付已全部满足当前验收 | 依 accepted closure 契约关闭该批，立即说明父提案剩余范围及一个后续入口。 |
| 当前只映射设计，但已授权目标含实施且没有独立交付依据 | Design Reviewer 派发 Chief Designer 核对原目标及最小映射；不静默收缩范围或由审查员自行扩大映射。 |

第三种情况的纯技术映射核对复用已有授权、计数和设计，不自动增加 Design Review；确有实质设计变化才应用现有设计审查条件，实质业务范围/风险改变才使用负责人决定出口。批次真正完成或等待时依现有规则选择 close/continue，不为了保持流转而强派实施。

### 2. 关闭提示与后续输入准备分清边界

在 `payload/docs/ai-collaboration/README.md` 增加一个短共享小节（建议锚点 `design-to-implementation-relay`），包含上表与独立交付依据；Execution Batch、Closed Batch Guidance、角色卡、workflow 对应段落及矩阵短引该规则，避免多份完整算法。

合法独立设计 close 的 Current Status 第一段与最终回复，显示“设计交付完成；父提案仍有 <已核对事项>；下一步可发送 <具体请求>”。这是一条可复制的用户请求，不是关闭批次的 Operator Command；close 仍是 Next role none，不增加下一角色或能力行。

当前请求明确要求继续父提案，或“继续”结合已记录授权只有一个无歧义就绪范围时，按现有 Task Intake 准备后续输入，先保存旧关闭。当前只要求设计/评审并停止时，本轮只完成相应交接或关闭说明，不利用父提案授权越过角色边界。无授权、多候选无先后依据或事实冲突时，给实际剩余范围与最小请求/恢复方向，不猜测目标。

替代方案：在每个 Design Review 后必定关闭再建实施批次，会制造重复输入和计数归属问题；一律禁止设计 close 又会破坏合法设计交付。共享判定与短引用能复用现有规则，并让例外有据可查。

### 3. 只在真实边界核对已有事实

负责保存交接的角色核对 current-task、handoff、所引 Review 与唯一 tasks.md；如果活动任务叙述还写“尚未评审”，而当前 Review 已通过，则修正这一过时事实，说明本次 review 只覆盖的实际范围。不会要求把每个微步骤的状态写入所有文件，也不会把稳定目标、验收或历史 Review 改成另一种口径。

模板只增加短提醒。入口 Skill 引用共享规则，不新增状态检查清单或自然语言匹配器。旧设计 close 缺少新解释时保持可读，不补写历史、重开原批或降低计数；后续工作按真实授权与验收关联已有历史。

### 4. 修改范围与兼容

| 实施位置 | 最小变更 |
| --- | --- |
| `payload/docs/ai-collaboration/README.md` | 共享判定、独立设计关闭的首段提示，协调现有批次及关闭后接续章节。 |
| 同目录 `workflows.md`、`agent-prompts.md` | 协调 Chief Designer、Design Reviewer、角色出口和 Routing Matrix，引用共享判定。 |
| 同目录 `handoff-schema.md` | 在原有范围/关闭/持久化段落短引，不改变机器 schema。 |
| 同目录两个模板、`skills/ai-collab-start/SKILL.md`、`skills/ai-collab-continue/SKILL.md` | 原出口增加短引用与事实一致提醒，保留全部现有授权、恢复、能力和人工接力边界。 |
| `agent-rules.md` | 将批次的 phase 描述明确为交付验收范围，避免按角色结束解释关闭；受管标记与归属规则不变。 |
| 两份 operator-guide | 用虚构提案分别说明同批接力和独立设计关闭的用户操作。 |
| 根两份 README、两份 CHANGELOG | 对应用户行为的简短说明，变化进入 Unreleased；不更新发行版本与 snapshot。 |

不新增部署文件或调整安装集合。规范 Agent 契约保持英文，双语人类正文各用对应语言。实施时用链接复用共享说明，避免向多个入口复制整张判定表。

### 5. 有界验证与审查安排

以下 `demo-approval-flow` 为虚构提案。逐项保留输入、实际适用规则、预期路由和检查结果；这是路由推演，不冒充真实跨平台 Agent 演练。

| 场景 | 具名输入 | 预期可观察结果 |
| --- | --- | --- |
| R1 同批实施待办 | 1.1 设计完成、2.1 实施未完成，评审通过，累计 2，无有限上限 | 同批 dispatch Implementation Engineer，C3，累计仍为 2，人工转交。 |
| R2 独立设计交付 | 已确认的接口方案交付完成，仅映射 1.1；父提案 2.1 待办 | close accepted；首段展示设计范围/剩余项/具体接续请求，无下一角色/Operator Command。 |
| R3 关闭后明确实施 | R2 之后当前请求要求实施 2.1，授权及依赖适用 | 保存旧关闭，经 Task Intake 准备新映射后人工交接；相关历史按真实验收范围关联。 |
| R4 映射不一致 | 只映射 1.1、原授权目标含实施，没有独立设计交付依据 | dispatch Chief Designer 作最小核对，不 accepted close、不静默扩张，不自动重复 Design Review。 |
| R5 无授权或多候选 | 只有设计授权，或后续 2.1/3.1 无可确定先后依据 | 说明已知状态和最小后续请求，不自行开新实施范围或重复确认已明确内容。 |
| R6 即时环境缺失 | 下一实施动作需要人类准备，证据为未就绪 | continue blocked，Resume condition 与环境提示准确，不以 close 结束。 |
| R7 远期验证依赖 | 下一动作可离线执行，真实联调环境仅后续需要 | 派发安全实施，远期信息无需当前操作/回复，不声称真实验证完成。 |
| R8 有限授权用尽 | R1 加有效有限限制且累计已到 through，实施未完成 | 现有负责人决定出口；不能继续派发或通过重命名取额度。 |
| R9 角色范围限定 | 当前要求只做 Chief Designer 后停止，整批实施尚未完成 | 设计交接 dispatch 后停止，不自行执行实现，也不误记 accepted close。 |
| R10 活动叙述过时 | current-task 尚称未评审，Review 与 tasks 已证实设计完成 | 真实边界纠正已有活动叙述，范围和历史保持真实，不增加状态台账。 |
| R11 第二轮通过 | design-review-round=2、PASS，累计 2，无其他阻断 | 按 R1 或 R2 的实际范围选路，不因轮数终止父提案。 |
| R12 旧关闭缺新说明 | 历史设计 close 没有新版独立交付解释 | 原记录可读且不被重开/补写；明确后续请求按现行授权处理，未知事实不猜测。 |

实施检查分两部分：对上述表逐项静态核对所有受影响入口；在 GUID 命名的可丢弃镜像中选 R1/R2/R4/R6 代表结构，使用原 validator 及与场景相符的虚构 tasks/Review/命令核对期望批次、动作、角色、累计和修订。证明的是结构与指定值；文本语义由静态走查与独立审查核实。只有新事实扩大影响时才增加检查，不重跑未变的全部安装或解析套件，不新增只匹配措辞的测试。

End-to-end feasibility：在现有文件、路由及校验接口内有界可行，无新依赖或业务环境前置；能展示用户可读的预期下一步。LLM 是否始终遵循仍是未观察事实，结构通过不证明实际宿主行为。

Design Review Decision：`no`。本方案澄清已有范围与出口，无新增架构、公开机器接口或复杂度例外，首个完整批次可以通过具名交接展示操作结果；实施后由独立 Code Reviewer 作一次聚合 M 审查。出现真实复杂度例外或实质设计变化时再按现有触发条件处理。

一个 Execution Batch 覆盖全部修复、说明、检查与独立审查，唯一清单为 tasks.md；本轮只完成设计，所有实施/审查项保持未完成。设计和普通检查不是 verdict；本批现为 0，未来实际审查单调记录，现无额外有限授权行。

## Risks / Trade-offs

- 共享规则增长仍可能增加读取负担 → 用短共享小节、角色短引用和现有区块内的一段摘要，不建立第二手册或增加每轮表单；不承诺 token 节省。
- 将独立设计交付限制过紧可能导致不必要往返 → 允许已确认设计目标和有依据的独立契约交付，不引入新的批准要求；只有实际范围冲突交 Chief Designer。
- 复用父提案授权可能被误解为自动继续所有角色 → 同步强调当前请求和人工接力停止边界，关闭后的 Task Intake 与执行下一角色分别处理。
- 自然语言规则不能可靠地被结构校验器推导 → 保留结构接口，结合具名静态场景及独立审查；不增加高成本语义引擎。

上述副作用以较小的共享说明和现有证据步骤控制，无新增业务取舍需要负责人批准。未观察的宿主行为继续如实报告。

## Migration Plan

本次仅准备设计，产品改动由下一次明确启动的 Implementation Engineer 执行；既有 User 授权无需再次询问，但本轮首席设计师角色边界必须停止。后续发行仍使用现有完整包、受保护升级与 clean staging 流程，不在本批实施安装或版本准备。

旧运行态及 Review 不要求迁移回填；恢复或接续保留已有真实计数、有限授权和未满足验收。若将来回退包，使用已核对的完整发行包和既有保护流程，不能混合新旧规范或覆盖项目证据。
