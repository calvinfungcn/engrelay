# Design

## Context

动机见 proposal.md。此设计适用 v1.9.4 源码，仅改变既有说明及交接输出提醒。

已核对的起点：

- canonical README 的 Minimal Authority / Lean Design、角色中的范围审查及 ce-simplify-code 已覆盖未来设想越权、最小方案、局部抽象和必要安全例外。P0 的工作是用场景核对并只补实际缺口，不重写这些原则。
- Task Owner Progress Visibility 已要求成果、证据和剩余工作；Process Metrics 已可选，但没有统一可选 L 级/人工投入的口径，也未区分“无新增通过项”与研究/审查的有效进展。
- Common Preflight、schema 能力章节及两个交接模板已要求能力首行；三个入口 Skill 的 Output 没有直接提醒这一容易遗漏的出口细节。
- 根 README 的 may add / 可增加，操作指南的 may also show / 可增加，均容易把建议性质理解为可以不写。该事实不能证明外部项目某次遗漏的真实原因。
- validator 只检查已有结构/预期状态及可选计数；能力行有意不作为机器字段。Current Status 则参与既有来源恢复的完整内容比较。

设计工件用于跨 README、角色共享说明、入口和模板之间的技术取舍；不因为需要 design.md 就新增一次设计审查。

## Goals / Non-Goals

**Goals:** 在同一真实交接中，让人类读到简短成果与必要的可选估算，并让新 Agent 派发的档位提示更难遗漏。估算和成果正文不挤占能力首行，也不改变机器结构、恢复或独立审查。

**Non-Goals:** 不增加指标工具、validator 告警/参数、必填字段、实时计划、模型选择、统一规模缓存或新运行文件。P2 不在本次任务内。详细需求及兼容边界以增量 spec 为准。

## Decisions

### 1. 最小方案与可行性

采用现有区块中的说明性增补和出口回读提醒。没有新增服务、依赖、数据对象、公共机器契约、权限或归属边界；不扩张用户已确认范围。

| 验收方向 | 已有起点及最小落点 | 核对方式 |
| --- | --- | --- |
| 小任务不过度设计 | 复用 Minimal Authority、Lean Design 和现有审查分类；没有缺口便不改角色卡 | 对照简单复用、明确授权抽象和安全例外样本 |
| 可选估算 | 只在 canonical README 的既有 Process Metrics 段落集中定义 L 参考口径、投入区间和省略条件 | 无估算直接执行、混合文档/代码、基线缺失与规模偏差样本 |
| 成果可读 | 在 Task Owner Progress Visibility 补充中途真实边界的表达及有效进展判断，模板仅一个注释示例 | 成果/证据/剩余工作、研究有进展但尚无通过项样本 |
| 档位不漏写 | 共享 Common Preflight 明确本次派发回读同时看能力首行；三个入口 Output 短引用同一规则 | 实际文件/响应输出与最后回复相符；不靠 validator 猜测 |
| 公开说明一致 | 修正两版根 README 与两版 operator-guide 中可省略措辞，保留 schema 唯一默认表 | 双语语义与既有默认/覆盖规则核对 |

End-to-end feasibility decision：proceed。现有路径足以实现，无需 spike、外部环境或负责人重新选择。限制是提示词无法保证所有模型每次遵从；本次目标是消歧及减少遗漏，不是宿主强制守门。

舍弃“先增加 validator 非阻断告警”的备选：它仍需新增围栏/区块定位、缺失/非法档位处理、旧输入诊断和双宿主检查，并修改当前不纳入机器校验的说明。当前没有证据表明出口提醒无法满足有界目标，先付出这些成本收益不足。若将来仍有可靠漏写证据，再独立选定告警范围。

### 2. 共享信息放置与规模口径

L1–L5 的参考区间集中维护一份，沿用 spec 的产品源码 Added + Deleted 口径；测试、文档、生成及机械变更另述，不代表其不需审查。人天仅在需要且有依据时给人的有效投入区间，既有 Expected implementation sessions 原义不变。无合适口径就省略，不以所有模块平均值或全仓体量代替受影响范围。

有实际 Git 数据时须说明批次起点和路径范围，并区分已提交、暂存、未暂存、未跟踪及无关变化的覆盖限制；不将单独 git diff 的数字当整个批次。无需为此编写脚本或提供新的统计命令教程。

当前结果及偏差放在已有 Current Status / Delta / Known Risks / Authoritative Evidence / Review Or Task State Impact 的合适位置。默认只说有变化且有用的事实；验收项数量不是默认表单。进度复核关注新增证据和未知项收敛，不维护“连续两次交接”计数。

模板只增加一处英文注释示意，例如成果已自测、证据路径、尚待审查；不是完整交接替代件。不增加 Progress/Estimate 标题或枚举，不修改 current-task 模板。既有回读继续核对实际状态，新的摘要同样受完整 Current Status 恢复比较约束。

### 3. 能力提示在现有出口一次核对

唯一能力定义/默认表保留在 handoff-schema.md#capability-tier-guidance。共享规则只补“建议的值不构成资格门槛，但新 Agent dispatch 的建议行必须输出”；在已要求的交接保存/回读中一并确认行的位置、默认/明确覆盖和将复述的档位。

三个 canonical 入口 Skill 的 Output 用短提醒链接该锚点，不复制表格或让 Agent 调查模型。文件和 response fallback 保持同一规则，后者仍如实说明未落盘；human dispatch、continue、close 不增加能力行。已有有效缺行交接不回填、不拒绝。写入失败或真实只读时执行原有完整 fallback，不借补档位绕过权限。

agent-prompts.md 仅维护共享出口说明；workflows.md 或模板如已有清楚引用就不重复增补，只有为当前语义连贯所需才作短修改。ce-simplify-code、安装器、管理规则、validator 与已有测试代码均不在选定改动内。

### 4. 文档和追踪

根 README 双语各增加简短成果/可选估算说明，并把能力提示的“可增加”改为“新 Agent 派发须给出参考”。双语 operator-guide 修复相同歧义，不重写其他人类指南。共享契约及机器示例继续英文，OpenSpec 工件使用中文。

CHANGELOG 双语仅记录本次实际实现的 Unreleased 变化及验证范围，不改版本号或历史发行。OpenSpec 双语导航以一行链接本变更并注明已确认待实施；P2 单列待决定并说明不是本次承诺，不复制任务状态或运行数据。以上文档修改均留给实施，本轮只创建规划。

### 5. 聚焦验证与证据边界

在可丢弃、虚构输入中作下面的开发验证，复用已有模板和 validator，不安装到源码或真实项目。这些样本不是新增的产品角色或日常工作环节。

| 场景 | 观察重点 |
| --- | --- |
| 单一简单修复；Excel 需求但没有 PDF 授权 | 沿用局部方案，未来框架不进入必做，S 快速路径不变 |
| 用户明确授权插件扩展；一行权限修复 | 有依据抽象/安全处理不被最小设计禁止，L 级不改变实际风险及独立性 |
| 大量机械文档变化；没有工时/工具/可信起点 | 可省略 L/人天，不扫描安装，不因规模自动停止或要求重构 |
| 研究排除错误方向；明显投入却无解释进展 | 有效证据不误报停滞；真正偏差只给最小复核动作，不用固定交接次数 |
| start、requirements、continue 生成新 agent dispatch | 实际输出的能力首行/回复一致、默认规则正确、命令完整、成果不挤占首行 |
| response fallback；human dispatch；continue；close；旧缺行记录 | 适用动作显示/省略正确，真实权限及旧兼容保持，不伪称 validator 检查了档位 |
| 带可选摘要的真实边界及已关联恢复来源 | 保存/回读/预期校验及完整 Current Status 比较保持；无后台指标写者或历史回填 |

取同一候选输入，使用现有模板在虚构目录实际保存并回读新派发和旧缺行交接，以 validator 的预期参数检查适用结构；能力首行和最终回复需人工或独立读者核对。附命令、退出码、观察输出与输入对应，运行时间仅在实际采集时记录。无需为每条自然语言新增措辞匹配测试或重跑全部恢复/安装套件。

另用实际可用 Agent 在上述代表性简单/安全/无指标/旧记录与新派发场景作受限路径抽查，直接读取候选 canonical 入口，不改生成发现副本、不调用新增外部模型服务。可聚合多个场景到少量开发会话；保留实际输入、生成交接及回复。若因宿主能力或权限未完成某条，明确缺口，不能用模板填充或结构成功替代模型遵从证据，也不能提前勾选覆盖这些要求的任务。已授权范围内优先用当前宿主可用能力，新增服务/费用等实质变化才用既有负责人出口。

仅比较候选差异是否增加重复规则、固定步骤、必读材料、工具调用或交接；没有可比 token/耗时证据不声称效率提高或设百分比目标。validator 等脚本字节保持时，其匹配范围历史证据可复用；本批新增结构样本只证明这些具体输入。

### 6. 风险与审查安排

本批 M。Design Review Decision：no。选定方案没有复杂度例外，首个完整批次可展示一次含成果摘要及正确能力行的真实派发；仅因横跨文案文件不增加独立设计审查。保留最终一次独立 M 代码/协议审查，合并检查授权、提示词成本、旧兼容及实际证据。当前累计 verdict 为 0；若后续出现新复杂度例外，先停止该扩张并按原 Chief Designer / Design Review 规则处理，不在本设计中默认放行。

整个变更作为一个连贯批次，文件编辑和场景核对是内部步骤。所有真实 verdict 在同批累计，清单不因修订/角色更换而重置。

## Risks / Trade-offs

- [提示词和 handoff 增长] → 定义集中、出口短引用、示例只一处；可选数据缺省省略，不新增固定汇报节点。
- [LOC 优化反而损害质量] → 数字仅解释范围；保留安全、授权抽象、测试与真实复杂度例外，不以数字评分或验收。
- [能力必写被误当资格门槛] → 同时写清新输出责任、建议性质和旧记录兼容；不改 validator 退出语义。
- [仍可能漏写] → 实际 Agent 小规模抽查并如实报告限制；不承诺零遗漏或用新治理系统掩盖遵从性问题。
- [摘要引发恢复冲突] → 只在原有真实边界由负责者写入，沿用修订/来源/回读，不对 Current Status 添加比较豁免。

## Migration Plan

本轮只准备工件和映射，主 spec 待后续完成后按既有归档流程同步。实施只维护本变更 tasks.md，旧 handoff、Review 和归档不迁移；私有开发证据保持忽略。

本次不更新发行 snapshot、不提交或发布。后续获相应发布请求时才按干净 git archive staging 重建完整清单；官方升级仍保护既有归属、单一 SkillTarget 和项目内容。若撤回本次源规则改动，按本批最终差异回退对应解释与提醒，不改真实任务历史或已记录验收。
