# Design

## Context

动机见 [proposal.md](proposal.md)。本次是 Full 已发布路由的来源判定补充，不改变授权模型或工具运行逻辑。

| 已检查位置 | 现状与本次需要补齐的衔接 |
| --- | --- |
| `payload/docs/ai-collaboration/README.md#minimal-authority-rule` | 已限制建议和推断成为权威，但没有明确要求保留影响范围的最小来源及整体目标／本轮职责的区别。 |
| 同文件 `#design-to-implementation-relay` | 已有同批实施、独立设计关闭和映射核对三分支；依据主要来自任务叙述，尚需防止叙述本身是无据推断。 |
| `workflows.md#1-task-intake`、canonical start 的任务准备 | 已记录目标、范围、验收及人工接力，需要把最小来源核对纳入已有步骤。 |
| Chief Designer、Design Reviewer、continue、handoff-schema | 依赖当前任务和映射选路；需引用来源规则，并协调现有“只纠正过时事实、不改稳定验收”的边界。 |
| 两个模板、agent-rules、双语 operator-guide | 可以复用现有 Source／Goal／Constraints 及出口说明，无需新表单。 |

已观察到上游范围解释影响下游关闭的路径；不能仅凭某次设计关闭认定审查员违规，也不能从一般实施意图证明全部后续动作均已授权。公开方案仅用虚构 `demo-order-flow`。

## Goals / Non-Goals

**Goals:** 下一 Agent 能从短输入核对来源、整体目标、当前职责和适用授权；设计完成后作出有依据的交接、核对或合法关闭；不增加重复批准和机械审查。

**Non-Goals:** 不恢复全部聊天，不添加来源账本、字段／枚举、语义校验器、安装路径或运行引擎；不改变 Lite、manager、validator、生成宿主 Skills 或已关闭历史。本次设计没有新增业务要求或扩大原修复授权。

## Decisions

### 1. 最小来源保留在已有任务区块

在 Full README 的 Minimal Authority Rule 附近增加唯一共享小节 `task-scope-evidence`，说明 [spec delta](specs/collaboration-package/spec.md) 的来源要求。Task Intake 在现有 Source、Goal、Scope 或 Constraints 中用必要的一至三句保留影响当前范围／出口的请求摘要、明确决定或适用规范引用，区分已确认内容和推断。不是每项都须引文或统一填写四栏；简单明确任务沿用简短原输入即可。

例如：“已授权修复 demo-order-flow 的完整问题；本轮只做首席设计和交接；后续实施仍在已授权范围。”另一个不同输入是：“本次请求为方案和估算，实施授权尚未确认；不得解释为用户明确禁止。”不得用第二种摘要替换第一种来源。

已有确认过的任务／规范摘要可作为最小依据，不要求原始逐字聊天。在接入或实质范围更新时记录；同角色微步骤不反复写入。未来会话读取当前输入和具名依据；有材料冲突时仅核对所需出处。缺失来源本身不使旧记录失效，也不触发全历史扫描；只在影响当前实质决定且无法从现有权威确定时，使用已有恢复方向或 Owner Decision Brief。

替代方案是原始聊天归档、逐项来源表或语义解析器，会增加隐私暴露、token 和维护成本，且不能认证授权；本方案不采用这些机制。

### 2. 先核对来源，再按原有三分支选路

整体目标是用户想得到的结果；本轮职责是当前角色应执行到哪里；实际授权决定可执行哪些工作。三者可以重合，也可以不同。先做方案不会撤销已明确的实施授权；背景中的最终实施意图和“没有禁止”也不足以自动取得所有实施权限。

用户直接请求的方案或估算本身可以是独立交付，不要求再取得一句“只做设计”的批准；但已有完整实施授权时，仅因当前角色是设计师、任务只映射设计或当前回合只做设计，不能重新定义整体验收。设计交付是否独立，必须能由请求目标／已确认契约说明，不能由 Agent 自写的范围排除循环证明。

复用 `design-to-implementation-relay` 的原有三分支。增加来源冲突与映射冲突相同的最小核对出口：Design Reviewer 不自行扩权或修改产品需求，派发 Chief Designer；Chief Designer 依据已确认来源纠正无据推断及映射。纯来源说明或映射纠正、没有实质设计变化时不再做 Design Review，不重复申请已明确的授权。真的需要新增业务、风险、成本或实施权限时才使用原负责人决定规则。

当前只确认独立方案时，可完成方案验收后关闭并说明未明确的后续授权与具体入口，无需为一个未请求的未来实施动作强设当前等待。若未能确认本批验收边界，则先核对，不以含糊来源发布 accepted。普通 accepted 仍需原有证据和最终输入校验。

### 3. 后续明确授权与稳定验收协调

continue 的当前请求如果明确补足后续实施授权，按已有 closed-batch guidance 和 Task Intake 处理，保留旧关闭及真实相关审查历史，不受早前 Agent 的无据“禁止”结论束缚，也不要求重新发送等效授权。

原来的“只纠正过时活动事实，不改变稳定验收”继续适用：纠正无据推断不能被说成改写用户验收；用户真正改变业务范围时，由有权角色按已有决定流程记录。不能把来自用户的新决定伪装成文字勘误，也不能用来源核对绕过审查额度、等待或角色权限。

角色停止和人工接力保留。本提案覆盖完整修复；当前只做设计的指令只限定本轮行动，设计完成后派发适用角色并停止，不执行接收者，也不 accepted close 本修复。

### 4. 有界实施位置

以下路径均为现有路径，不增加部署集合。规范 Agent 内容保持英文，人类说明成对更新。

| 范围 | 实施位置与最小变更 |
| --- | --- |
| 唯一共享规则 | `payload/docs/ai-collaboration/README.md` 的 `task-scope-evidence`；原设计接力和关闭后接续章节以短引用协调。 |
| 流程及角色 | 同目录 `workflows.md` 的 Task Intake、Design、Design Review 和相应矩阵；`agent-prompts.md` 的 Common Preflight、Chief Designer 与 Design Reviewer，避免复制整张规则表。 |
| 持久化与模板 | 同目录 `handoff-schema.md` 中 current-task、事实协调和关闭依据的相关短句；`templates/current-task.template.md` 与 `templates/handoff.template.md` 提示在现有区块表达来源和范围。 |
| 入口与管理规则 | 同目录 `skills/ai-collab-start/SKILL.md`、`skills/ai-collab-continue/SKILL.md`，以及根 `agent-rules.md` 的必要短引用；不修改本机生成 OpenSpec 或宿主 Skill。 |
| 人类说明 | 同目录两份 `operator-guide`，根两份 README 及两份 CHANGELOG。加入对应简短例子和 Unreleased；不改版本、既有发行段或 snapshot。 |

共十五个现有产品／说明文件；不强求每个位置重复相同文字，原引用已足够的地方保留即可。只扩展唯一共享说明会遗漏入口在接入时形成错误范围的路径，因此相关入口和角色需一并核对。

### 5. 具名验收与检查

下面均为虚构来源，表是路由验收数据，不是第二实施清单。每个场景保存给定请求、最小任务输入、适用规则位置、决定的出口、发现和限制，不用一个“PASS”替代来源／映射对应。

| 场景 | 输入与预期可观察结果 |
| --- | --- |
| S1 完整授权，本轮只设计 | 已授权修复 demo-order-flow 的完整缺陷，本轮仅 Chief Designer；设计完成后 dispatch Implementation Engineer，C3，原未完成实施仍映射，人工停止。 |
| S2 独立方案和估算 | 唯一确认目标是可独立验收的方案／估算；满足所需评审后可 close，首段显示设计完成、已知父待办和具体后续请求；不声称用户禁止实施。 |
| S3 无据缩窄 | 来源含完整实施授权，任务却声称“用户只允许设计”且仅映射设计；评审出口 dispatch Chief Designer 作最小核对，不关闭或擅自实施。 |
| S4 总体意图，实施未知 | 背景想实现功能，当前仅请求方案、估算；准确保留已确认规划范围和后续授权未知，不自动授予整个提案实施。独立规划交付满足时按 S2；本批边界仍无法确定时先核对。 |
| S5 明确暂不实施 | 用户明确要求本次仅交付独立方案；不得派发实施。相关验收与评审满足时合法 close，不新增设计-only 批准步骤。 |
| S6 下一平台无聊天 | 当前任务保留最小确认依据和具名规范，无冲突；下一 Agent 可按正常路由执行，不要求导出整个聊天或逐项来源表。 |
| S7 关闭后明确实施 | S2 后用户明确实施单一可确定未完成范围；保存原关闭，经 Task Intake 准备映射，复用设计和授权，保留相关历史，不重复审批或重评审。 |
| S8 有效有限上限 | S1 加真实有效且已耗尽的有限授权，实施仍未完成；按原负责人决定出口等待，不通过来源新措辞、换批次或新提案绕限。 |
| S9 旧记录缺来源短句 | 旧任务缺新版摘要但现有明确权威足够；继续读取正常路由，不回填历史、不因缺句阻塞。有具名实际冲突时只核对缺口。 |
| S10 纯来源／映射纠正 | 核对确认原设计、验收和风险未变；Chief Designer 纠正解释及映射，保持实际计数，不自动追加 Design Review。 |
| S11 后来决定与原推断区别 | 新的明确 owner 请求补足权限时，由有权角色记录适用依据；真实业务变更仍按原决定规则，不能用“只改叙述”隐藏改变。 |

实施时聚合静态走查 S1–S11 与受影响的入口、角色、模板、双语解释和 spec 场景对应。必要结构检查只取 S1/S2/S3/S8：在 GUID 可丢弃镜像中构造相符任务、清单、来源和必要 Review，使用未改动的原 validator 传入场景预期 batch/action/role/round/revision，记录真实命令、子进程退出、诊断和参与输入指纹。S8 的合法等待应通过；若验证不可执行派发的反例，其非零必须明确是预期拒绝。

validator 和安装投影未改动，不以 prose 更新为由重跑全部双宿主安装／升级套件；已有脚本行为证据只有在输入／范围匹配时可复用。上述代表输入是新构造时，应记录其本次实际运行，不借旧夹具通过替代。检查证明结构与指定值；来源语义由静态走查及独立审查核对，不声称实际跨模型遵从、业务验收或 token 节省。真实付费平台演练不属于本批门槛。

### 6. 批次、审查与职责

一个完整 M 级批次覆盖全部规范、入口、说明、检查及独立审查，以 [tasks.md](tasks.md) 为唯一实施清单；所有实施／独立审查项在本轮保持未完成。

端到端可行性：现有 task/handoff 区块、角色与校验接口足以表达最小依据和各出口，没有新增依赖、业务环境或复杂度例外；可交付的是可核对协议及说明，不是模型必然遵从的保证。

Design Review Decision：`no`。当前澄清已有范围权威与角色出口，没有新架构、机器接口或权限模型；虚构交接能展示完整结果。实施后由独立 Code Reviewer 聚合检查全部验收、最终差异、场景对应、双语与交付隐私。若实施发现实质设计变化或复杂度例外，再按已有条件处理，不能仅因新增一个来源短句触发重评审。

关联修复的适用历史、实际累计值与单次关闭后审查分别见当前运行态及原索引；不将旧 verdict、运行态或私有路径复制进新提案。原 accepted archive 保留，新名称不清除同一未完成行为验收的历史或有限限制。设计和普通结构检查不计 verdict。

## Risks / Trade-offs

- 将来源要求变成逐条举证可能增加 token 和机械阻塞 → 仅在现有任务区块保留影响范围的最小依据，复用具名确认材料，旧记录无强制回填。
- 一律关闭规划批次可能掩盖已有完整授权；一律派发实施又可能扩权 → S1–S5 明确区分来源，不要求用户额外批准合法独立方案。
- 多处重复说明易产生冲突 → 一个共享小节，其余短引用和小例子；不增加第二规则表或日志平台。
- 自然语言仍可能误读 → 指明“来源不明”与“明确禁止”的区别，保留最小核对及实际负责人决定；结构检查不认证授权。

以上均在当前修复范围内可用较小方案处理，无需新增统一批准步骤。高成本替代如完整聊天取证或语义引擎先另评估收益、隐私及较小选项，不在本批建设。

## Migration Plan

本轮仅准备正式产物并保存下一角色交接；下一位用户启动的 Implementation Engineer 使用本设计及实际清单实施。旧批次和归档保持原样，相关历史只关联不重写。后续发行沿既有 clean export、snapshot 和受保护升级流程按适用授权处理，不在本设计行动中准备版本或操作真实项目。
