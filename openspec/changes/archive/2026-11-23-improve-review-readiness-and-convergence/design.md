# Design

## Context

动机见 proposal。现有 Full/Lite 规则已有同角色连续工作、聚合修复、证据复用、独立审查及无进展处置，但对何时形成完整审查输入、同一验收多次局部改善仍反复往返、目标型指令与人工交接的关系，缺少足够明确的联动。计数本身不是默认阻断；单独存在的有限负责人授权、明确的提前检查以及 H 修复后的独立验证仍然有效。

本变更是一个 M 级、spec-driven 批次，预计 1–2 个实施会话。首个可观察成果是：用虚构场景说明负责人指定的实现角色如何连续完成一个具备可演示主路径的成果、执行直接相关检查、聚合必要审查，并准确保留未验证和危险路径限制；以已修改的规范、场景推演和必要的定向检查作为检查方法。现有能力与范围见 current-task；不引入新服务、依赖、状态、公共 API 或复用层，复杂度例外为 none。

## Goals / Non-Goals

**Goals:**

- 在既有角色和授权下，使实现、日常检查、修复和正式独立复核各有清晰边界，以可交付结果而非微小动作决定通常的检查时机。
- 对连续往返但仍未完成的同一验收进行低成本整理，避免计数或发现编号变化掩盖真实状态，同时不抹掉已经获得的进展。
- 保持跨平台人工接力、用户指定的检查节点、高风险独立性和既有有限授权；Full 与 Lite 在各自流程内采用相同原则。

**Non-Goals:**

- 不变更既有结构化 handoff 字段、安装清单、管理器、验证器、调度方式、权限模型或默认审查上限，不创建新的角色、追踪表或强制遥测。
- 不修改历史审查、重新计算或重置已有计数，不承诺特定 token 节省；不把规范或结构检查描述为模型遵从的证明。
- 不将虚构示例当作真实业务验收，不授权现场设备、资金、生产数据、发布、部署或跨角色自动运行。

## Decisions

### 1. 在适用节点聚合，而非每次局部修改都正式交接

在 Full 的现有共享协作规范中增加一个短小的就绪规则，角色和流程章节只链接或简述其适用方式。负责角色在现有范围内持续实现完整主路径，执行与当前改动直接相关的低成本检查，并聚合关联修复；已有依赖、明确的用户指令、项目强制检查和安全前置始终优先。形成约定的可观察成果及足够审查输入后，再按风险与既有规则交接进行聚合独立审查。明确列出未覆盖路径和未验证内容，不要求先为每项微小进度建立新批次或正式评审。

不选择“每次修改后都重新进入独立审查链”，因为它与已有聚合规则重叠；也不选择“直到开发结束才允许任何检查”，因为它会掩盖风险、违反显式门槛。固定评审次数阈值或新增审批字段均不采用。

### 2. 分清开发检查、受控试用和最终验收

开发中允许执行当前授权范围内的相关检查；试用候选只描述已实现、可安全运行的部分及已知限制，不等于最终通过。对不可控的危险路径，不对外声称可试用：应先修复、禁用或仅在获授权的隔离条件下试用；真实设备、资金、生产数据、外部部署或其他实际副作用继续服从原有权限和安全要求。独立审查、H 修复后独立验证、显式的更早门槛和最终验收不能因试用而省略或虚报。

不引入默认的试用审批环节；选择直接复用风险和授权规则，既不让不安全试用发生，也不因无副作用的局部试用打断已授权开发。

### 3. 两次实际往返后的短整理

一次往返指：针对同一尚未完成的映射验收完成一组修复，并取得相应独立复核或验证 verdict；开发期本地检查、重复命令、设计讨论及其他验收的 verdict 不单独计为一次。若已有连续两次此类往返，且该验收仍需再进入正式修复/复核，则即使已有局部进展，也在进入下一次往返前，由当前已有权限的负责角色引用现有结果，简短记录：已独立确认的改善、仍阻断验收的事项或新回归、以及最小的聚合修复和证据计划。整理本身不是新的 verdict，也不改变 Review round、有限授权或独立性。

整理完成后继续现有授权内可执行工作；若下一步骤必须由另一角色执行，则保存人工交接并停止，不自动启动或代行下一角色。无明确授权、必须的业务/风险决策、实质超出约定的成本等真实问题仍按现有规则处理，其他安全且独立的工作可继续。已到有效有限扩额上限时不得开始新的循环；原同一问题无进展、反复产生新问题的既有停滞规则仍适用。两种分析时机重合时一份分析即可满足两者，不能叠加两次角色交接。

每次整理只依据现有相关记录和交接，不增加台账；已有整理后，只有同一验收又实际产生两次新的修复与独立复核往返且仍需继续时，才再次触发。历史无法确定时保留未知，不编造往返、重置历史或无限追溯；不把总 Review round 或单独运行的验证命令直接当作往返数。采用此轻量触发器，而不按总轮次固定阻断或一有新发现便强制负责人授权。

### 4. 缺陷分流与证据复用

按当前被检验的验收、实际影响和证据区分真正阻断、尚未验证以及可延后的建议。影响安全、身份、并发、资金、数据或实际契约的真实问题不得因追求速度降级；纯机械格式或风格修正若项目要求完成，可与相关改动和后续适用检查一起处理，不因为单独修改一行必然新建完整正式往返。证据仅在输入、环境与覆盖范围仍匹配时复用；实际变化影响的证据必须补充，未知保持未知，修复不等于已独立验证。

选择复用现有 finding、交接和证据语义，不新增字段或独立评分机制；不以“非阻断”绕过项目、用户或法定的强制检查。

### 5. 入口、目标型请求及 Lite

Full 新任务使用 start 建立输入，不由入口擅自实施；同一未完成批次可按当前交接的合法接续语义使用 continue，也可按 start 的既有同批委托路径处理，不能因此重置或新建同范围审查历史。目标型请求授权实现目标，并不自动跳过适用的独立复核、用户明确指定的步骤或人工跨角色交接。若用户指定本轮只执行一个角色，保存下一角色可复制的交接后停止。独立审查由非实现/修复作者执行，用户要求完整独立审查时按实际授权范围执行。

Lite 只在其短规则中补充适用的就绪、试用和整理原则；保留既有 Executor/Reviewer、队列、等待、独立性、扩额和 lite-1 状态格式，不为与 Full 对齐引入新角色或硬门槛。已有旧交接不需要迁移、补写历史或新增机器字段。

### 6. 修改位置、验收与交接

以 `payload/docs/ai-collaboration/README.md` 为 Full 共享规范入口，按实际矛盾在 `workflows.md`、`agent-prompts.md` 及 canonical `skills/ai-collab-start/SKILL.md`、`skills/ai-collab-continue/SKILL.md` 使用短链接或必要提示；Lite 在 `lite/RULES.md` 内做对应的最小修改。公共行为变化同步 `README.md`、`README.zh-CN.md`，必要时同步既有中英文操作指南，并更新已有 Unreleased 记录；不复制规则到所有上下文。仅当核实现有模板、schema 或其他文档确有冲突时，在既有格式内作最小同步。

使用本变更两个 spec delta 的正反场景作为检查依据，涵盖连续实施、显式提前检查、目标型提示的人工接力、试用边界、H 独立性、两次往返及二次触发、有限授权、证据复用与旧状态、Lite 队列。优先做小型虚构场景推演和受影响文档/入口一致性检查；真实宿主试验若不可用则记录未覆盖，不能以静态通过推断 Agent 遵从或 token 消耗。需要额外高成本实验时先说明成本与较小替代，不以真实项目为夹具。

**Design Review Decision: no。** 未发现新服务、依赖、数据对象、公共 API 或其他需要例外处理的复杂度；本批可产生上述可观察成果，适用规则未要求单独设计审查。实施后仍由独立 Code Reviewer 按 M 级和用户要求审查，不由实施者代行。若实现发现需要实质改动安全边界、机器校验或其他复杂度例外，暂停受影响部分并按现有设计升级规则处理。

## Risks / Trade-offs

- [连续实现被误读为跳过独立审查] → 明确目标型请求不覆盖检查节点、角色独立与人工交接，并用显式审查请求场景验证。
- [为尽快试用暴露真实危险操作] → 先修复、禁用或在已授权隔离环境内限制相关路径，并明确可试用范围和未验证事项。
- [两次往返成为新的固定硬上限或新增重复流程] → 它只触发一次现有角色的简短整理，既不自动停工、增加 verdict，也不改任何有限授权；与旧停滞分析合并。
- [将必要问题错误分类为格式建议或复用过期证据] → 依据实际影响、项目约束和证据输入核对；安全相关缺陷与受影响证据继续阻断相应验收。
- [自然语言过长或模型仍不遵循] → 一处共享规则、少量入口提示与 Lite 简述；区分静态检查和真实宿主观察，避免承诺收益。

## Migration Plan

1. 在本变更中实施 Full/Lite 和双语说明，保留现有字段、角色和兼容语义；用受影响场景与链接检查验证。
2. 新安装版本按既有发布流程生成完整快照；在本次授权内不生成发布包、不安装到真实项目。旧项目继续使用自己的既有 handoff，升级后保留相关历史及有限授权。
3. 通过常规版本回退恢复旧规范；本变更不涉及数据迁移。回退不应删除既有交接、审查或负责人授权记录。
