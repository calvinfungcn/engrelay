# Design

## Context

见 proposal。已发布 Full 契约中，正式 Agent `dispatch` 有可复制指令和 C 档，同角色 `continue` 可由已接入的合格 Agent 执行；这些机制不启动或唤醒进程。Lite 的已批准就绪队列默认由活跃 Agent 顺序继续。两套验证器都只允许现有三种 Human Action Required 值；Lite 还固定十一字段。现有中文指南将 `none` 描述为无需人工介入，不能准确说明人工转交。

## Goals / Non-Goals

**Goals:** 在正常角色边界支持用户选用不同工具和额度；让 Full 新任务默认可人工接力，并保持明确自动接续、真实等待、Lite 旧队列和独立审查。

**Non-Goals:** 不实现进程级禁止或自动调度，不添加机器字段、枚举、模型映射、固定平台、成本台账或新的审批。仅规则不能保证所有宿主遵循，也不能证明节省 token。

## Decisions

### 1. 以 Task Intake 确定接力边界

Full 新任务指现有同项工作核对后，确需建立新任务输入的任务；不按文件时间、版本号或会话名称猜测。Task Intake 在现有 `Constraints` 用一条普通文字记录人工接力默认；用户明确要求自动启动已授权后续角色时记录该具体范围。接收者从当前任务和 handoff 沿用这条边界，当前请求的明确较窄限制优先。只说“实施”不自动等于授权跨角色自动启动。

已存在的未关闭任务优先沿用可证实的既有选择、授权、实际归属和最新 handoff，不强行回填或切换；没有明确偏好不构造历史自动授权。若现有证据不足以确定接续的权限或唯一写者，报告具体未知并维持现状。可安全完成的当前角色工作不因此增加等待。

人工接力作用于正式 Agent `dispatch`，包括同角色交给另一 Agent：保存、回读、按预先决定的状态校验后，在回复说明转交并结束回合。不得通过同会话改名、子代理或 CLI/API 启动下一角色绕过边界。单角色内相邻工作及用户已启动后的可执行 `continue` 保持原规则；人为结束同一角色会话时沿用已有 Continuation Command。自动接续的明确选择不授予额外业务权限，不能绕过禁用功能、工具权限、真实等待、额度或独立性。

备选是每次执行前要求负责人批准，或一律不允许自动执行；前者增加无意义往返，后者破坏明确授权的用户工作流，均不采用。

### 2. 显示真实的人工转交，保留机器兼容

在 handoff 标题后用一行普通文字说明“需人工转交”，保留 `Current Status` 首行 C 档；最终回复首先给出下一角色、建议档位、Operator Command 所在位置和如何转交。仍使用现有 `dispatch`、状态和字段；不能为转交虚构负责人决定或环境阻塞。

将相关人类指南对 `Human Action Required` 的说明限定为已有决定／环境等待摘要：`none` 不能证明没有人工转交。旧消费者可能仍按原文将 `none` 解释为无需任何操作；该限制须如实说明。真实决定／环境等待仍以原值与原条件表达。

备选新增 `awaiting-dispatch`：能供机器区分，但现有 Full/Lite 校验器会拒绝新枚举，超出本批兼容范围；留待单独评估。普通说明不是结构字段，也不能宣称让旧工具理解新语义。

### 3. Lite 保持既有队列默认

在 Lite 现有任务或项目约束中明确指定人工接力时，正式 Agent dispatch 停下；当前任务关闭且已有下一条批准队列项时，保存并协调已完成任务和队列，给出用户启动该条目的 Lite 入口后停止。不将已关闭任务伪装为仍有下一角色，不创建未获授权的新任务。未选择人工接力时就绪队列继续，不修改项目自有配置实例；现有可执行 continue 和真实等待原样保留。

备选将所有 Lite 队列都改为人工接力会改变已采用队列用户的行为，且超出已确认方案，因此不采用。

### 4. 可携带的交接与权限

共享工作区时，接收 Agent 读取最新 handoff、当前任务及具名权威，再检查执行归属、实际额度及权限。非共享或只读工具只能根据用户审核后提供的最小资料工作；不能读取最新状态或写回时使用既有响应交接，说明未持久化，并在原工作区由有权写者做来源修订／SHA256 匹配后再发布。不得自动上传项目、凭据或私有资料，不能将文件被复制视为全局最新或已获安全脱敏。

### 5. 范围、可行性与审查决定

现有 Current Task、Operator Command、C 档和三种动作足以承载人工边界；Lite 已有项目限制和队列。最小方案不引入持久格式、依赖或新服务，具备可实现的端到端路径。首次可观察成果是：虚构的 Full 新任务从首席设计师形成有效实施派发，回复显示人工转交，当前回合不启动实施；用户在接收会话检查最新文件后执行既有授权。以输入、手工场景和真实结构检查核对；仅在另有适用授权且成本相称时补有界真实宿主演练。无实际调用证据时，宿主遵循保持未验证。

风险初判 M；一个执行批次覆盖 Full 边界、Lite 兼容和相关说明。设计审查决定：**不单独增加 Design Review**；没有新增复杂度例外，已有可观察首个成果，后续 M 独立代码审查覆盖实际差异和兼容性。当前累计 verdict 0，默认上限 3；设计者不自审。此设计不扩大用户已确认范围。

## Risks / Trade-offs

- [默认变化影响旧习惯] → 在新任务与发行说明中明确人工默认和自动覆盖；已有任务保持已证实授权，不自动重写运行态。新 Full 任务习惯自动推进的用户需明确选择，属于预期行为变化。
- [旧 `none` 消费方误读] → 顶部人类提示和文档明确转交；机器消费者仍可能误判，保留该已知限制，不宣称彻底修复。
- [Agent 忽略自然语言边界] → 多个入口和输出一致表达，使用受影响场景核对；这不是强制隔离，缺真实宿主证据时不得声称全面遵循。
- [跨平台冷启动增加 token、操作或泄露风险] → 不强制每个微步骤换会话，交接只引用必要证据，非共享资料由用户审核；不承诺 token 节省或自动脱敏。
- [角色停止与已授权 continue 混淆] → 区分正式 dispatch 与已启动同角色 continue；`close`、真实等待和审查额度保持原义。

## Migration Plan

产品实施时更新 canonical `payload/`、受影响入口与双语说明；不修改历史 handoff、项目实例或管理器配置。新任务在创建输入时采用人工默认；老任务沿用可证实的已有边界。使用虚构可丢弃夹具核对新版规则和旧结构，发行时按既有干净导出流程生成快照；发布及真实安装需另有请求。若需回退，按既有受保护的包版本恢复流程处理，不自动回滚或改写运行态。
