# Design

## Context

动机见 [proposal.md](proposal.md)。本仓库现状支持在既有职责内收敛，无须引入运行时能力：

- Full README 的 Review Round Circuit Breaker、Evidence Reuse、Proportional checks and owner choice 已规定默认三次累计 verdict、有限授权、聚合发现和输入匹配复用；agent-prompts 的 Code Reviewer／Fix Engineer／Verification Reviewer 及 workflows 的 Formal Review 已引用这些规则。
- Full review-round 模板已有 Scope、Evidence、Conclusion、Broad evidence reused 和 Additional checks run，可承载范围、证据和复核说明，不需新增必填字段。
- Lite RULES 自带三类职责、同一验收累计计数、有限扩展及评分；Lite 只有 task／handoff 等模板，没有单独 review 模板，故在现有 task 模板中增加简短提示即可。
- operator-guide 的现有证据示例及 Lite README 可承载人类说明。新增受管路径会牵涉布局演进，收益不及直接修改既有文件。
- OpenSpec 两份主规范已有对应行为；本变更只提供 delta，规划阶段不同步主规范，不改真实项目或历史 Review。

## Goals / Non-Goals

**Goals:** 为负责人要求的完整审查、修复复核、关闭后追加工作及归档核对给出可执行边界；用五类虚构输入观察实际 Agent 判断，并在一个 M 维护批次完成独立审查。

**Non-Goals:** 新角色、评分体系、审查账本、语义／脱敏校验器、新机器字段、受管路径、宿主矩阵、运行时编排；不修改原发布版本、根快照、安装器或生成宿主 Skill。

## Decisions

### 1. Minimal Option 与责任归属

集中修改 Full 现有 README，在相关角色／流程写短引用；Lite 在自身 RULES 保持最小自包含。只在现有模板内补说明，人类指南用对应语言解释一次，技术标识与 Agent 契约保持英文。行为要求见两份 [collaboration-package](specs/collaboration-package/spec.md)／[workflow-profiles](specs/workflow-profiles/spec.md) delta。

该方案不扩大已确认范围。替代方案是新建通用审查手册、增加机器状态或自动扫描平台；这些会增加必读、安装映射和误阻断成本，本次不采用。规则／示例和受影响检查先后实施，但共享同一验收、批次和额度，不拆成两套生命周期。

### 2. 完整审查与复核如何选择

| 实际请求／变化 | 当次责任 | 可复用及结束条件 |
| --- | --- | --- |
| 负责人明确要求完整审查 | 独立审查全部已授权验收、最终差异、兼容性、证据、说明及交付隐私；一次聚合发现 | 可以复用匹配的测试证据，不能因过去有 PASS 而跳过本次明确追加请求 |
| 无追加请求，已有独立结论覆盖当前全部输入 | 核对结论仍适用 | 不制造一轮相同审查，也不为普通 S 任务新增归档门槛 |
| 已确认问题的局部修复 | 核对原问题、修复差异及实际受影响行为 | 引用未变输入的既有结果；全部指派问题及验收满足即可收口 |
| 新真实缺陷、共享行为变化或原证据失效 | 说明失效依据并扩大检查 | 扩大到因果关联的调用者／输入；如需覆盖全部验收则完整复核，范围外问题按既有发现规则处理 |
| 只有规范同步与归档 | 核对 delta／主规范、完整性、状态／索引及隐私 | 按当次影响定级；授权的核对通过即结束，不派发只复制状态的角色 |

“全部验收”取本次明确授权的范围，不把最近一次修复路径冒充整个提案，也不把无关父项目变成新范围。Full 的 H 修复独立验证和 Lite 的相应独立性保持；文案不是自动 S，原任务 H 也不自动使每次归档为 H。

### 3. 证据对应与报告隐私使用现有段落

Scope 说明已审版本或差异，以及相对前轮的实际变化；Evidence 给出具名来源及其入口、输入、环境、实际结果的适用关系；Conclusion 简述复用、失效证据及剩余验收。这是既有正文内容，不新增字段、统一表格或每条命令重复的全套元数据。

已有命令、退出码、版本或指纹足以对应时直接引用；元数据不是越多越好。旧证据只有在相关输入仍匹配时适用；旧上传成功不能证明 FileId 成功，离线结果不能替代明确要求的认证 HTTP。无法取得的事实记未知，并依据原验收判断影响，不能把所有宿主内部信息变成新增门槛。

审查者在现有交付步骤检查报告自身，包括适用的工作区／待提交副本；输入中的私有值不进入报告、交接、工具输出或含值差异。示例使用虚构别名／计数，不从 WM 拷贝原文、运行态或发票。普通错误通过新记录勘误；历史敏感值按适用授权最小移除，保留事实、verdict、评分与无私有值的处理说明。既有隐私原件受项目边界控制，不创建新的原始备份或集中日志要求。

### 4. 关闭后范围与额度，不重置也不重开历史

| 情况 | 处理与授权 |
| --- | --- |
| 原验收尚未完成，只是换阶段／名称 | 沿用同一验收和实际累计数，不能通过先关闭再改名取得额度 |
| 未关闭批次已到 N，明确只追加一次审查 | 沿用已有有限扩展字段，按真实授权记录 from=N、through=N+1、范围与证据；不是追加三轮修复 |
| 已关闭成果收到一次追加审查请求 | 原快照及计数不改；经现有入口建立具名关联的有限审查范围，记录其实际 verdict，不声称旧批重新打开，也不把新记录的局部计数解释为默认三轮授权 |
| 审查发现具名新缺陷 | 先记录影响及修复建议；已存在适用修复授权就复用，没有则走既有负责人出口；真正新增修复可建立关联批次，但原未完成验收改名不属于新缺陷 |

单次请求限制的是授权动作范围，不改变三轮结构校验的机器语义。不新增跨批次总计字段或改造 budget parser；索引／任务简述关联原记录及历史计数即可。结构校验成功不能证明授权真实，也不能代替按 scope 核对执行边界。原有限授权键、绝对上限和批次匹配方式全部保留。

### 5. 归档和评分保持有界

独立归档核对仅在负责人明确要求或现行适用约束需要时安排，不作为所有任务固定新门槛。同步改变规范要求或引入矛盾时按实际影响处理；全局检查的其他历史失败与当前归档结果分别说明，不能虚报全局通过，也不要求修复其他提案才能结束。

只保留已有实施／修复评分。在本轮已有证据揭示返工来源时，用一句话说明来自实施、修复、证据判断或审查产物；未知就写未知。报告自身引入隐私问题不能自动归给被审实现，最终修复 5 分不替换早期评分；不新增审查员评分或归因调查。

### 6. 实施路径和唯一权威

| 既有路径 | 允许修改 |
| --- | --- |
| payload/docs/ai-collaboration/README.md | 审查范围、证据、关闭后授权和归档的集中规则；现有评分节补归因说明，保留旧锚点 |
| payload/docs/ai-collaboration/agent-prompts.md、workflows.md | Task Intake／设计／审查／修复／验证／收尾的必要短引用，避免复制整段规则 |

| payload/docs/ai-collaboration/lite/RULES.md、lite/templates/task.md | 等价自包含短规则及模板提示，不引入 Full 角色或手册依赖 |
| README.md、README.zh-CN.md | 对应公开概要，区分源码候选改进与已发布版本 |
| payload/docs/ai-collaboration/operator-guide.md、operator-guide.zh-CN.md | 在现有说明／示例中解释完整审查、局部复核与有限追加授权 |
| payload/docs/ai-collaboration/lite/README.md、lite/README.zh-CN.md | Lite 人类说明及短例，不维护第二套完整规范 |

不新增 payload 文件，因而不需要安装布局演进。handoff-schema、管理器、校验器、Skill、根发行 snapshot 和版本保持现行职责；若实现发现必须扩大这些范围，先解释因果关系及更小替代，不自行扩张。

### 7. 五类有界场景和取证方法

实施 Agent 用候选规则处理五个固定的虚构场景，保存实际输入、可得调用／会话信息、候选规则版本或指纹与真实判定。预期答案只作检查依据，不能预填为观察；夹具中的命令／退出码须标为虚构输入，不能作为本项目实际执行结果。可在一次有界检查中覆盖五类，无需五次正式审查或全宿主组合。

| 场景 | 输入与可观察预期 |
| --- | --- |
| 场景1：错误证据（Full） | 旧版本上传成功被引用为当前 FileId 成功；实际判定保留对应验收未验证，说明缺口，不建议无授权供应商调用 |
| 场景2：局部脱敏（Lite） | 报告带有明确禁止交付的虚构私有标识，行为及既有检查输入未变；产出不含该值的修正及聚焦复核，核对适用交付副本并复用相符行为证据，不重跑全部套件 |
| 场景3：扩大影响（Full） | 修复改变共享契约且旧断言不覆盖新行为；实际判定沿调用者扩大检查，保留不受影响结果，不能以局部修复为由直接通过 |
| 场景4：有限追加（Lite） | 包含原未关闭批次 N=3 只追加一次审查、已关闭快照追加审查两个小变体；前者上限为 4，后者保留历史且只执行所授权审查；发现缺陷不自动进入新三轮修复 |
| 场景5：归档结束（Lite） | 完整实现证据未变、当次规范／归档对应检查无缺陷，另有无关历史归档失败；实际判定分别说明结果、结束当前核对，不承诺全局通过或新建复述审查 |

这些是本维护批次的实际 Agent 场景检查，不冒充虚构业务中 M/H 的独立 verdict；本批累计数只由真正的维护审查产生。Full／Lite 检查的是各自规则下的边界决策与产物，不证明实际安装、全新 Lite 会话隔离或所有宿主遵从；不可得信息明确未知。Code Reviewer 在本批既有聚合审查中检查真实输入／输出及修复，不另加评分或演练审查。

若采集实际判定的方法尚未验证，先对场景1 取得一个最小输入／返回对应，再继续其余场景；无真实输出的项保持未完成，不以更多说明代替取证。静态引用／语言、虚构私有标识的输出泄露及现有机器字段／路径集合核对可用一次性检查；不增加措辞匹配测试或通用采集脚本。

## Design Review Decision

- 独立 Design Reviewer：`no`。本方案以既有有限授权、独立性、产物和计数机制补充说明与例子，无新服务、依赖、数据对象、公共机器接口、认证模型或跨功能抽象，必要复杂性例外为 none；首个场景可展示完整判定路径。跨 Full／Lite 的文档一致性在本批独立 M 聚合审查中核对。
- 当前完成 verdict 为 0，默认总额 3；规划／结构检查不是 verdict。实现后独立 Code Reviewer 为本批第 1 次，必要集中修复／复核继续同一计数，不自动重审干净结论。若出现实际新复杂性或 H 范围，按既有路由处理，不预先豁免独立性。
- 下一角色 Implementation Engineer，建议 C3；实现仅可完成 tasks 的实现／自检项，独立审查及关闭留待实际角色和证据。

## Risks / Trade-offs

- [规则变长、Full／Lite 漂移] → 在各自现有权威集中维护，其他位置只写短引用；Lite 保持自包含，公共字段不变，不新增每次必读文档。可检查增删范围，但不以固定字数作验收。
- [聚焦复核被误作跳过缺陷] → 明确真实新缺陷、共享行为变化和证据失效时扩大检查，原必须修未复核不通过。
- [关联新批次变相清零或阻断真实新修复] → 区分未完成原验收和具名新缺陷，保留授权范围及旧计数引用，不新增全项目总额度或把历史三次用尽变成永久禁止后续任务。
- [增加报告隐私检查却再次泄露] → 虚构案例、无值摘要、报告自身及交付副本检查合并在现有步骤，处理日志不复制私有值；不宣称自动识别所有秘密。
- [场景观察被过度推广] → 只报告实际输入／输出和证据边界，不宣称节省固定 token、全宿主通过或 Lite 安装行为已验证。

## Migration Plan

本次只维护源码规划，后续实施只修改已存在的受管内容和源码审查记录。旧 handoff、评分、任务和配置不回填、不迁移；现有安装不会在本任务中被升级。正式发行时再按现有干净导出与 snapshot 流程处理版本，本批不提前重建根发行快照。回退仅针对本变更引入的规则／说明差异，不改历史或其他工作。
