### CR-01 — 默认反馈与用户可见出口不完整

Full README 明确写 “may add”，Lite 的独立日常权威 RULES 也仅写 “may add”。两份根 README 同样表述为“可附”。这允许 Lite Reviewer 在已有实施／修复审查中直接不提供任何反馈，偏离已批准的“默认附分数或无法评分”。Full 两个角色卡只要求写 review conclusion，所有新条款均未要求最终回复简短复述，用户只看最终答复便可能收不到已批准的反馈。

这是正在实现的产品契约缺口，并非要求追补某份旧审查的评分，也不应把一次评分遗漏变成新的业务验收门槛。最小修复：在已有权威中对齐默认提供、not scored、现有结论与最终回复短复述，双语同步；保留不增审查／不改通过标准／不回填旧报告，当前遗漏只在已有保存步骤补齐。对应 2.3、2.4、3.1；用现有固定输入走查即可。

### CR-02 — M 修复的角色卡与总规则冲突

总 README 指定 M 修复由 Code Reviewer 评价；该角色也确实以完成的 implementation 或 fix 为触发。但新增局部指令只处理 “an implementation delivery”，并以 “Rate only the implementation” 收尾。M 修复复核者按角色卡执行时会跳过应有的修复评价，或误评前次实施；H 的 Verification Reviewer 已接入修复评价不能补偿这个正常 M 路径。

最小修复：让 Code Reviewer 在已有 M 修复复核中评价本次 fix、引用已指明发现及送审版本、解决程度／必要证据／回归，保留前次评分，不评价其他角色、不另开审查。对应 2.3；复用固定脱敏修复输入核对 M 与现有 H 指引，无需实际制造缺陷或增加评分会话。

### CR-03 — 示例缺少真正的发布动作

示例明确把完整返回写入 named container，接着回读并运行 expected-state validation，却没有将通过来源匹配的完整 Action State 发布到实时 .ai/handoff.md。若旧 live 仍 dispatch Reviewer，照此操作会继续留着旧路由；带目标 revision／action 的预期核对会失败，仅保存容器不能完成发布。示例也只列 Task ID，未点明 Full 恢复必需的 source batch 身份。

最小修复：双语示例引用已有 source-matched-recovery，简述匹配来源 batch、prior revision／SHA256、归属／额度、冲突保持原状；在可写且匹配后，保存原始返回并发布其完整实时 handoff、回读后再按目标值校验；不改技术结论、不重复计 verdict，无写者保留完整未落盘响应。无需复制整套算法或增加字段／文件。对应 1.2、3.1；以明确旧状态与返回状态作聚焦走查即可。
