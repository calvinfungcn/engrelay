### CR-01 — 已出现的有限授权行可以被当作不存在

位置：`payload/docs/ai-collaboration/lite/scripts/validate-state.ps1:119`、`payload/docs/ai-collaboration/scripts/validate-runtime-state.ps1:150` 和 `:939`。Lite 只在决策值以裸 `review-budget-extension` 或其反引号包裹形式开头时识别授权。虚构任务 T01 的 `from=4; through=6`、Review round 6：裸行与反引号行均 exit 1，双引号包裹的同一行却 exit 0；Full 对等的带引号行 exit 1。对包含同一结构行的缩进列表，两套脚本均 exit 0。即使这些写法按格式判为无效，也不应将可见的结构化限制当作不存在并允许路由；删除默认计数门槛使这个结果成为可用路径。按已接受格式一致识别，或对可辨识但无效的行阻断，同时保持普通自然语言决定的既有含义；补齐 Full/Lite 的到期、非到期、派发与接续针对性检查。

### CR-02 — Full 将真实 blocked 等待误当成可执行 continue

位置：`payload/docs/ai-collaboration/scripts/validate-runtime-state.ps1:925`。`$routeIsGated` 仅排除 `awaiting-owner-decision`，没有排除 `blocked`，虽然同文件 `:798` 已明确将后者视为非执行状态。虚构的合法 `continue/blocked` 有恢复条件且 round 6：没有授权行时 exit 0，加入本批 `from=4; through=6` 后 exit 1，提示只能等待负责人决定。设计 `3` 要求真实 blocked 仍可表达，恢复为可执行状态时才重新检查额度；Lite 的非执行 blocked 路径也不调用额度门。应区分记录真实等待与实际执行，并覆盖到期及恢复后的边界。

### CR-03 — Lite 未规定有限授权行的后继携带和来源比较

位置：`payload/docs/ai-collaboration/lite/RULES.md:49`、`:162` 及 `payload/docs/ai-collaboration/lite/scripts/validate-state.ps1:199`。Full 手册明确要求在后继、恢复与响应交接中原样携带有限授权行并与来源比较，也披露脚本无法发现丢行；自包含的 Lite 规则没有这项义务或限制说明。实际虚构来源匹配：prior 为 round 5、`from=3; through=6`，候选为 round 6 并遗漏该行，提供有效 prior SHA256、来源元数据和目标修订后，Lite 仍 exit 0 并输出来源匹配。脚本无法从单个新状态推断丢失是已知限制；问题是 Lite 负责角色缺少必要的保护规则。补齐 Lite 原样携带、来源核对与未检测限制，保留实际有限授权和历史。

### CR-04 — 关闭后已有持续授权的唯一下步仍被旧指引禁止

位置：`payload/docs/ai-collaboration/README.md:1098`、`payload/docs/ai-collaboration/skills/ai-collab-continue/SKILL.md:75`、`README.md:293`、`README.zh-CN.md:226` 和双语 operator guide 的关闭提示。新段落允许已有父提案持续授权且唯一就绪、依赖和权限明确时经 Task Intake 接续；紧邻的旧段落却规定仅说“继续”时必须列清单并请求指定项目，Skill 又要求当前请求自身清楚指定并授权后续工作。具名静态输入“已有持续授权 + 唯一就绪项 + 用户继续”因此得到互相排斥的指令，违反 1.1 和 delta 的 `Continue an already authorized parent change` 场景。应在入口、权威规则和双语说明统一区分已可确定的持续授权与真正含糊、无授权或过期的请求，保留人工转交停止。

### CR-05 — 旧默认三次等待的恢复例外未进入实际接续分支

位置：`payload/docs/ai-collaboration/skills/ai-collab-continue/SKILL.md:89` 与 `payload/docs/ai-collaboration/README.md:607`。升级完成后，若原 Owner Decision Brief 证明确实只因旧默认三次等待，工作已有授权且无其他等待，设计 `3` 和 DR-07 允许引用依据恢复；Skill 的 `awaiting-owner-decision` 分支仍无条件要求适用回复后才能继续。该入口会把不再需要的回复变成阻塞。应仅在证据满足所列迁移条件时处理该旧等待，真实负责人决定、有限授权和未知情形仍保持原有保护。

### CR-06 — 来源匹配恢复仍将三次 verdict 当作默认上限

位置：`payload/docs/ai-collaboration/handoff-schema.md:71`、`:1212`。来源匹配步骤仍规定候选 Review round ≥3 且派发 Agent 时，必须带有效有限追加行，否则保留旧状态；同文件还保留 `default-three circuit breaker`。因此一个没有明确有限授权、来源与修订均匹配且仍有已授权工作的第四次交接，虽然新校验器允许，恢复规则却会拒绝。该命中并非设计审查专属次数或历史文献，DR-06 扫尾和实施结果的剩余命中判断不成立。应按适用的实际有限授权、真实等待和来源比较保护恢复，不能仅凭数值阻断，也不能删除原有有限行保护。

### CR-07 — 固定一个修复循环的旧指令仍限制正常工作

位置：`payload/docs/ai-collaboration/workflows.md:34` 和 `payload/docs/ai-collaboration/README.md:1340`。两处仍要求每批至多一个 review → fix → verification 循环；同一 README 的 `:526` 则允许在验收未完成时按新规则继续。一次修复后独立验证发现仍有实质进展、无明确有限授权和无停滞的同范围问题时，旧指令会单独阻止下一次授权内修复。应保留每轮聚合、独立验证和已给有限授权，同时移除与设计 `2` 不一致的固定单循环上限。

### CR-08 — 同一发现停滞后的技术处置与负责人等待互相冲突

位置：`payload/docs/ai-collaboration/README.md:568`、`:594`、`payload/docs/ai-collaboration/handoff-schema.md:846`、`payload/docs/ai-collaboration/lite/RULES.md:54` 和 `:68`。一组条文要求停滞后首先由有权角色在原范围内作一次技术分析，仅在确需授权、业务／风险取舍、实质成本或不能继续时找负责人；另一组却规定一旦停滞，只能关闭或等待负责人决定，未经有限追加授权不能派发技术角色。若识别停滞的审查者需要把分析交给有权的设计角色，规则无法同时执行，会产生设计明确试图避免的额外请示。应停止重复无进展修复，同时允许已授权的有界技术分析；达到真正的有限上限或需要决定时继续保护相应限制。

### CR-09 — Lite 停滞判断遗漏已独立验证的实质改善

位置：`payload/docs/ai-collaboration/lite/RULES.md:68`。设计 `2`、Full 手册和两份 delta 均要求“没有缩小根因／消除阻碍的新证据”且“没有独立验证的实质改善”才判定两个循环均无进展。Lite 只写前一条件。若某修复经独立核验显著降低同一问题发生率，但根因仍未知且阻碍尚未完全消除，Lite 会提前判停滞，Full 则不会。应把同一问题的已核验实质改善纳入 Lite 判断，并同步受影响的双语候选说明；不同问题的改善仍不能掩盖停滞。
