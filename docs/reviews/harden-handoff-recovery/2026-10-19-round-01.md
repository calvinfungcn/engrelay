### 一致性与可行性核对

- 四份工件互相对应：proposal 的四项变更 → design 第 2–6 节 → spec 四个 MODIFIED 需求 → tasks 十项（1.1、2.1–2.3、3.1–3.2、4.1–4.2、5.1–5.2）；与 `.ai/current-task.md` 的映射 ID 逐一相同，未发现第二份实施清单、新 Routing 字段、新动作/状态、状态库或运行引擎。
- 增量 spec 的四个 MODIFIED 需求名称均存在于主 spec；原有 16 个场景标题全部保留，并在其上增加新场景，没有静默丢失既有行为（归档时 MODIFIED 会整体替换需求，所以保留是必要条件）。
- 设计引用的源码事实已逐项核对为真：schema 的候选条件目前只依赖 review index；applied 条目前只比较 Routing 与 Operator Command；实现结果模板的 Next Action 仅有 Decision/Reason/Action State；Skill 第 1 步只提审查索引来源；`agent-rules.md` 第 52 行为 “real legacy execution”；`scripts/manage.ps1` 的 `Get-ManagedInsertion` 生成 `## Legacy ai-collaboration Workflow policy`，全库只此一处使用该精确标题，`Get-ManagedReplacement` 以清单中的精确 insertion 定位旧块并仅拼接块内内容，因此标题文案可改而不动保护算法。
- 来源可发现性：候选仅来自恢复前已存在的具体引用，不扫描、不选最大号、不让自引用取得权威；与 schema “targeted check … does not choose by time or number” 一致。Routing 的 `Next output files` 本就要求给出每个输出的精确路径，所以派发时点名结果文件不是新负担（见 DR-07）。
- 容器：复用结果模板的 Next Action，完整文件形交接放在更长外层围栏内，沿用现有指纹/修订号叙述，不加 Routing 字段；复制仅限确需之处，一次转移一份，成本有界。旧修订缺失时目标从 1 开始、不回填，与 schema 的 `State revision` 可选语义和 pending/advanced 判定相容。
- 比较面缺口属实：现行 applied 条目不比较 Current Status，而可执行 continue 的命令位于其中；增量后同 revision 不同接续将判 conflict，保守且保留 live。仅规范化行尾、保留嵌套命令围栏的要求与 validator 的围栏感知段落解析一致。
- 权限、独立性、额度：关闭、真实等待、额度耗尽与有限授权、独立性保护均先于恢复；实现完成不增加 Review round；实施者不得借恢复自审，与既有第 6 步一致。
- 项目侧：LOCAL-ENTRY-01 在公开工件中仅有通用描述；对变更目录检索具体项目名无命中；明确 deferred、不阻塞本批、不改真实项目、不手改受管块。`.ai/` 被 Git 忽略，本地证据不入库。
- 比例：不新增依赖、参数、字段或后台进程；validator 与管理器保护算法不变；一至两个实施会话的估计偏紧但已有 current-task 停止条件和成本说明兜底，属观察而非阻断。
