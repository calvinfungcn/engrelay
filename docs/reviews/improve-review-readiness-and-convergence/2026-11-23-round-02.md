修复已改善共享 README、工作流和实施角色摘要，但仍有以下直接影响同一验收的冲突：

1. `payload/docs/ai-collaboration/agent-prompts.md:105` 的 Common Preflight 写明用户仅指定当前角色时“stop without executing that role”。这里的 `that role` 指前句的当前角色，而非下一角色；它与同文件要求当前合格角色立即执行授权步骤、以及用户要求当前角色完成工作后停止相冲突。角色入口都可能读取该通用预检。
2. `payload/docs/ai-collaboration/skills/ai-collab-continue/SKILL.md:143` 接收一个 agent 派发后，`:155` 仍在用户指定仅执行当前角色时无条件要求后继交接和人工转交提示。这个分支描述的是进入当前角色的派发；当前角色完成后可能合法 `close` 或等待，不能因此推定存在后继 agent 派发。`ai-collab-start/SKILL.md:77` 也无条件要求人工转交，而同文件步骤 5 允许 Requirements Analyst 在同一责任会话行动及等待负责人决定。
3. `.ai/review-readiness-convergence/scenario-checks.md:219` 把负责人等待场景写为 `Next action: wait` 并标 PASS，但 `payload/docs/ai-collaboration/handoff-schema.md:837` 的合法动作只有 `dispatch|continue|close`。因此该记录不能证明合法负责人等待与单角色边界相容；正确等待仍须使用现有 `awaiting-owner-decision` 状态、对应动作和 Owner Decision Brief。

影响：用户要求“只执行当前角色”时，通用指令可能让 Agent 不执行被要求的工作；即便当前角色完成，入口仍可能指示虚构的后继转交。错误等待样本还遮盖了其中一个应核对的路由边界。

修复方向：在受影响的通用预检及 start/continue 入口按真实动作统一表述：完成当前已授权角色，只有实际派发给后继 agent 时准备转交；合法 close 和负责人等待按原规则处理。修正等待场景，并用虚构条件覆盖当前角色执行、agent dispatch、clean close、合法负责人等待及条件 Requirements Analyst 路径；记录实际依据和未知项。不得引入 `wait` 新动作。
