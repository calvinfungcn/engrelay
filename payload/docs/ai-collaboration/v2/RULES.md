# EngRelay v2 Rules

Activate ONLY when the current task explicitly selects `EngRelay` (or `WorkflowMode: default` without another controller). Discovery, `.ai/relay/` (including `CURRENT`), or historical files never activate it. Use one primary controller per task; never load the legacy `full` handbook or `validate-runtime-state.ps1`. OpenSpec (`proposal`, `design`, `specs`, `tasks.md`) is the sole requirement/task authority. Optional `docs/engrelay.config.md` supplies project commands and quota notes; blank entries never block planning and never waive required acceptance.

## 1. Risk, Difficulty, and Sizing Axes (Orthogonal)

- **Risk (`S|M|H`) + explicit review requirement** SOLELY govern review/verification gates (`C1–C5` never triggers review alone):
  - **Empty gate** (Risk `S` and no explicit user/project review requirement): implementer self-checks pass → close directly.
  - **M**: requires independent code review and independent confirmation of `BLOCKER` fixes.
  - **H** (auth, security, money, data integrity, cross-system contracts, migrations, release gates): requires independent code review AND independent post-repair verification (both executed in independent `review` mode; matching unchanged evidence may be reused).
- **Independence**: Reviewer/verifier MUST be an independent session from the implementer and fixer (no self-review; no self-verification of required `H` acceptance). Prefer a different model family; when unavailable, a genuinely independent same-family session MAY run `review` and MUST record its actual tool/model. Switching model family alone never proves independence.
- **Difficulty (`C1–C5`) & Workload (`XS|S|M|L` × `可断点|建议连续`)** guide platform/model/reset-window selection only (`XS`: 1–2 files; `S`: 3–5 files; `M`: 5–10 files or build/local-DB checks; `L`: dense single-window ceiling). Scope exceeding `L` MUST be split.

## 2. `plan` Mode (OpenSpec Orchestrator)

1. Read the active OpenSpec change (`proposal`, `design`, `specs`, `tasks.md`) and run one `docs/solutions/` lookup for matching pitfalls.
2. Slice into independently verifiable Work Packages (`WP-01..N`). Split ONLY where a reviewer can meaningfully reject one WP while approving its neighbor; fold config/tests/docs into the delivering WP. Never emit DTO-level micro-WPs or unclosable multi-repo monoliths.
3. Write `.ai/relay/<change-id>/board.md` containing:
   - `Global Constraints`: cross-WP hard invariants (exact field/column names, feature-flag defaults, forbidden actions).
   - WP table: `WP | Module | OpenSpec | Risk | Difficulty | Size/Rhythm | Review Gate | Deps | Status | Owner/Reviewer`.
   - Per-WP block: `Shape` (`ui|backend|concurrency|integration|docs|ops`), `Repo & Diff Scope` (affected repo paths, base ref/range or file boundary), `Interfaces` (`Consumes`/`Produces`), `References` (0–2 solution paths), `Deferred / Handoff` (explicit downstream WP for cross-boundary checks), and `Done & Verify`.
4. After `board.md` exists, write one-line `.ai/relay/CURRENT` for the `<change-id>` locked at entry.

## 3. `do` Mode (Platform-Native Execution)

1. Execute continuously inside the assigned WP: resolve local design details, implement, run required checks, and simplify diff. A resumed fix also reads the latest unresolved `BLOCKER` list and any recorded `(a)` authorization in `wp-XX.md`.
2. If actual risk exceeds the plan (e.g., `S` touches auth/contracts), immediately update WP risk in `board.md`/`wp-XX.md` and refresh the review gate; NEVER self-close via `DONE_WITH_CONCERNS`.
3. Direct-close (`[x] done`) ONLY when the WP's applicable independent review/verification gate is empty and checks pass.
4. On quota/session pause: append a ≤15-line `Checkpoint` (done / remaining / traps / next step) to `wp-XX.md` so another platform resumes `do` directly without triggering review.
5. On completion: write a ≤60-line summary in `.ai/relay/<change-id>/wp-XX.md` (status `DONE|DONE_WITH_CONCERNS|NEEDS_CONTEXT|BLOCKED`, actual repo/diff scope covering untracked/staged/committed files, commands run and input match, risks). On `BLOCKED`, change strategy (add context/upgrade tier/split/escalate); never blind-retry.

## 4. `review` Mode (Bounded Independent Review & `H` Verification)

1. **Minimal entry & scoped reads**: Start from `board.md` WP entry, `wp-XX.md`, and complete WP change scope (covering multi-repo, untracked, staged, and committed changes while isolating shared-worktree sibling edits). Read authoritative OpenSpec, module `AGENTS.md`, callers, and full source whenever needed to verify spec compliance or trace a concrete risk.
2. **Evidence & triage**: Confirm reused implementer test output matches current reviewed inputs; run targeted checks only for specific doubts or required `H` verification. Output ≤50 lines/round classifying: `BLOCKER` (P0/P1 real bugs, security/money/concurrency/contract/build failures), `NOTE` (non-blocking style/extra-coverage ideas), and `⚠️ Cannot verify from diff`.
3. **Review PASS vs Acceptance Complete**: `⚠️` allows `review PASS` ONLY when it does not block the WP's required acceptance AND maps explicitly to a named downstream WP in `board.md`. Without a downstream owner or when verification environment is unavailable, affected OpenSpec `tasks.md` items and the parent change MUST stay incomplete while independent WPs proceed. Only tick `tasks.md` when mapped acceptance is fully satisfied.
4. **Write allowlist**: `review` may write only `.ai/relay/<change-id>/`, `.ai/relay/CURRENT` when this call used an explicit `<change-id>` or a missing/stale pointer with exactly one valid board, and `tasks.md` only when mapped acceptance is fully satisfied. It MUST NOT modify product source, config, or tests, including after `FIX REQUIRED` or an in-session `(a)`. Record the verdict or bounded authorization (keep the cumulative count) and stop. The fixer session runs `do <change-id> <WP-XX>`; the same uncontaminated review session performs the next round.

## 5. Circuit Breaker & `[~] blocked` Recovery

1. **Hard 2-round cap**: Round 2 checks Round 1 `BLOCKER`s AND any real `BLOCKER` (new P0/P1, safety, contract, or build failure) in the fix's blast radius; only promoting `NOTE`s to `BLOCKER` is forbidden. Unresolved Round 2 or 2 consecutive identical failure signatures MUST halt immediately as `[~] blocked` (`failure_class: product|harness`), blocking only dependents and presenting 3 owner options (human intervene / defer / accept limits).
2. **Cumulative history**: Verdict count and failure signatures bind to the **unfinished mapped acceptance** in `board.md` `Progress Ledger` — NEVER reset by re-`plan`, splitting, renaming WP ID, switching platforms, or moving between WP and change-level reviews (§7).
3. **Recovery**: `harness` blocks resume once verified environment readiness holds. `product`/ceiling blocks require explicit owner choice: (a) finite bounded extra fix+review cycle (retaining history), (b) explicit deferral keeping `tasks.md` unchecked, or (c) distinct owner-limited acceptance (never recorded as technical verification pass).

## 6. Next Step Card and `.ai/relay/CURRENT`

1. **Next Step**: End `plan`, `do`, and `review` with one advisory card. Do not launch the next session, switch mode, or grant rounds. The card body is always these five lines, including when no alternate exists: `Primary` (exactly one lane), `Command` (one executable `do|review <change-id> <WP-XX>` or `plan|review|fix proposal|change <change-id>`, `Wait` with no repair or same-input rerun, or `none` when nothing is ready), `Axes` (Risk, Difficulty, Size/Rhythm), `Gate` (review/verification gate or the unmet recovery check), `Alternate` (one conditional ready WP, or `none`). A sixth line may send the fixer back to this review session. In-budget `FIX REQUIRED` and a recorded confirmed `(a)` may put `do <change-id> <WP-XX>` in `Command` without asking again or minting quota. An unauthorized `product`/ceiling `[~] blocked`, and a `harness` `[~] blocked` whose recovery is not yet verified, use `Command: Wait` for that WP.
2. **CURRENT lock**: `.ai/relay/CURRENT` is one trimmed line matching `^[A-Za-z0-9][A-Za-z0-9._-]*$` with no `..`, separator, or `:`. Resolve in two phases. (a) *Read-only identity*: an explicit `<change-id>` or a valid CURRENT locks the target for the whole call (later edits do not retarget it) and is echoed first as `Change: <change-id>`. Anchor = `board.md` for WP commands; an active `openspec/changes/<change-id>/` (not `archive/`) for proposal commands; for change commands, that directory or an existing `board.md`. Review reports never filter candidates. Only a missing or stale CURRENT falls back: exactly one candidate is selected; two or more, or none, lists candidates and stops (still ending with the five-line card: `Command: Wait`, `Gate` naming the ids to choose). (b) *Admission*: only after (a) and §7 checks pass may a call write CURRENT (explicit id or fallback) or any file. A refused call leaves CURRENT byte-identical or absent. `doctor.ps1` only reads CURRENT.

## 7. Change-Level Proposal and Change Review (`review|fix proposal|change`)

1. **Reports (append-only)**: `proposal` pair → `.ai/relay/<change-id>/review-proposal.md`; `change` pair → `review-change.md`. Use `## Round N`, `## Revision Feedback (Round N)`, and `## Recovery / Owner disposition`; never rewrite earlier verdicts, counts, or signatures. Change-level `Axes` take the highest WP risk in `board.md`, or `unknown` when none exists.
2. **Write allowlist**: `review proposal|change` appends its report (plus CURRENT per §6) and nothing else, including after `FIX REQUIRED` or an in-session `(a)`. `fix proposal` revises only `openspec/changes/<change-id>/*` and appends feedback; never product code. `fix change` fixes only confirmed defects in product, test, or config files, runs targeted checks, updates affected docs and `tasks.md` only when acceptance is satisfied, and appends feedback. Neither `fix` commits, archives, or releases.
3. **Same-acceptance inheritance**: change-level reviews and WP `do`/`review` share one cumulative count and blocked state per unfinished mapped acceptance (OpenSpec item plus failure signature), recorded in the report. Change-level commands never write `board.md`. The next WP `plan`/`do`/`review` that touches the acceptance mirrors the latest valid report verdict into both its `Progress Ledger` row and its WP table status; until that write, the report governs. Mirroring adds no verdict and never resets the count or signature. A PASS from an independent change-level review whose scope names the same mapped acceptance satisfies that acceptance's independent gate. When every such gate is met, the WP closes the acceptance (`[x] done`, `tasks.md` ticked) and recommends the next action without another review; otherwise the table and ledger name the remaining gate, and unfinished work is never marked done. A change review of an acceptance already blocked by two rounds (or by WP `[~] blocked`) reports it but inherits the block (`Command: Wait`); a change-level block likewise stops WP `do` on that acceptance. Different acceptance items and proposal-stage rounds are counted separately; a shared `<change-id>` never merges them.
4. **Fix admission (read-only, before any write)**: missing report → stop and name the `review` command; last round `PASS` without open items → stop; unauthorized `product`/ceiling block (including inherited) or unverified `harness` block → stop with `Command: Wait`. A refused fix writes nothing.
